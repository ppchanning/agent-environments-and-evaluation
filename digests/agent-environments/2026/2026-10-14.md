## 1. Morest: Model-based RESTful API Testing with Execution Feedback

来源：[原始页面](https://arxiv.org/abs/2204.12148) · [全文入口](https://arxiv.org/html/2204.12148v1)；Yi Liu; Yuekang Li; Gelei Deng; Yang Liu; Ruiyuan Wan; Runchao Wu; Dandan Ji; Shiheng Xu; Minli Bao；首发 2022-04-26，核查版本 v1。

一个服务可能允许先创建对象、取得标识符，再读取或修改它。即使接口说明列出了所有参数，测试工具也未必知道该把哪个返回值传给哪个接口；参数同名，更不意味着它们表示同一种对象。Morest针对的就是这种调用依赖不完整或不准确的问题：只按静态接口说明构造依赖，既会漏掉可行路径，也可能不断执行根本不成立的序列。它改变的不是服务实现，而是测试工具维护依赖关系、生成调用序列的方式。

输入是OpenAPI说明和可调用的REST服务。工具先建立“资源属性图”：把操作、数据结构以及结构中的字段联系起来，表达哪些操作生产某种数据、哪些操作消费它。随后沿图选择调用顺序，并把真实响应中取得的值缓存起来，供后续请求使用。运行结果又反过来修正图：响应揭示的结构可以补充关系，反复无法成功使用的关系可以被调整或删除。论文中的Petstore例子很直观：先创建Pet，才有机会继续测试相关操作；但Order和Pet都含有名为status的字段，静态匹配可能把订单状态误当成宠物状态。动态更新就是用实际交互纠正这种误连，而不是相信名字相同就存在数据依赖。[方法与示例](https://arxiv.org/html/2204.12148v1)

作者在6个实际REST服务上比较Morest、EvoMaster黑盒模式、RestTestGen和RESTler，并做移除图指导、移除动态更新的消融。主要表格采用每轮8小时、重复5次的设置；指标包含执行到的代码行和成功请求过的操作数。代码覆盖由测试期间的实际执行测量，不是模型主观评分。作者报告Morest在6个服务中的5个上有显著优势，消融也支持“图指导”和“运行中修正”分别有贡献。论文汇总发现44个问题，其中13个未被其他方法发现，并明确提到Bitbucket的2个问题获确认；不能把44统一写成开发者已确认的缺陷。[实验表2—3及第4.4节](https://arxiv.org/html/2204.12148v1)

证据限制：真实REST服务测试，未生成模拟器；CRUD过滤与服务集合限制覆盖范围。44项发现并非全部获开发者确认。可作为服务仿真的调用依赖验证参照。

阅读建议：第3节、表2、CRUD序列过滤规则；结合方法、结果和限制阅读。

## 2. DeepREST: Automated Test Case Generation for REST APIs Exploiting Deep Reinforcement Learning

来源：[原始页面](https://arxiv.org/abs/2408.08594) · [全文入口](https://arxiv.org/html/2408.08594v1)；Davide Corradini; Zeno Montolli; Michele Pasqua; Mariano Ceccato；首发 2024-08-16，核查版本 v1。

Morest依靠可推断的数据关系安排调用；DeepREST追问的是：如果真正的先后条件根本没有写进接口说明，怎么办？接口可能要求先完成某个业务步骤，后续操作才会成功，而这个条件不表现为两个参数之间的生产与消费。作者因此让测试器在真实调用中学习操作选择，同时学习参数该从哪里取值，而不是只枚举接口说明中已有的依赖边。

工具仍以OpenAPI说明和黑盒REST服务为输入。选择下一操作的强化学习策略，观察的是每个操作迄今成功返回2XX的次数组成的向量，并不是服务内部数据库快照。论文用购物示例解释：搜索商品成功之后，测试器可能取得可用商品信息，进而尝试加入购物车、结账。参数生成另设学习机制，把随机生成、说明中的示例、字典与已有交互经验等来源视为候选，根据成功经验调整选择概率；可选参数是否加入、数组长度也会学习。成功请求还会被再次利用，通过变异产生不同输入，包括缺少必填参数、错误类型或越界值，以探索更多代码和异常响应。因此它并非只重复成功请求，也有面向错误的变异阶段。[第3—4节](https://arxiv.org/html/2408.08594v1)

实验包含11个API，与RestTestGen、Morest、RESTler、ARAT-RL和Schemathesis比较。关键控制是每个API上各工具拥有相同的请求次数预算，预算按该API约一小时能处理的交互量估计；每组重复10次，并重启容器的文件系统，避免前一轮遗留状态。作者测量代码分支／行／方法覆盖、收到2XX的操作数，以及5XX故障指标。汇总结果中DeepREST的各项均值最高，但故障指标相对RESTler的差异没有达到所用统计检验的显著性；按API拆开也存在其他工具更好的个例。作者据此认为学习到了静态依赖难以覆盖的路径，但“究竟是哪条隐含业务条件被学会”并未逐一由状态真值验证，5XX指标也不能直接等同于开发者确认的独立根因数量。[实验第5节、图3—6](https://arxiv.org/html/2408.08594v1)

证据限制：成功计数向量不是内部状态真值；5XX不等于已确认根因。相对RESTler的故障差异不显著；提供真实API探索方法，不能视为模拟器保真证明。

阅读建议：第4.1节、第5.2节、图5；结合方法、结果和限制阅读。

## 3. AgentRx: Diagnosing AI Agent Failures from Execution Trajectories

来源：[原始页面](https://arxiv.org/abs/2602.02475) · [全文入口](https://arxiv.org/html/2602.02475v1)；Shraddha Barke; Arnav Goyal; Alind Khare; Avaljot Singh; Suman Nath; Chetan Bansal；首发 2026-02-02，核查版本 v1。

一条最终失败的agent轨迹可能含有许多错误，其中一些后来被修复，另一些只是更早问题的后果。让模型从头读日志、直接说“哪里错了”，容易把最显眼的异常当成根因。AgentRx的目标是找到轨迹中最早没有得到恢复、并与最终失败有关的关键步骤，同时解释错误类别。这个目标比找第一个报错更具体；论文的人工标注也围绕恢复关系，而非简单按时间选首个异常。

输入包括失败轨迹、工具模式说明，以及可选的领域规则。系统把消息和工具交互整理成统一记录，生成可检查约束：一部分来自工具及领域规则，另一部分依据已经观察到的轨迹内容。约束带有适用条件，满足条件才检查，避免把尚不该成立的要求提前判错。检查结果汇成带步骤和证据的违规日志，再交给LLM裁判结合错误分类清单判断关键步骤及类别。论文还比较逐步按前缀生成约束，与一次看完整轨迹生成约束；两者并非等价。检查既包含程序式条件，也包含自然语言语义判断，所以“可审计日志”意味着能追溯理由，不意味着每条判断都已机械证明。[方法第3节](https://arxiv.org/html/2602.02475v1)

作者整理115条失败轨迹：29条来自τ-bench的结构化API任务，42条来自Flash事件处理，44条来自Magentic多agent开放任务。人工标注提供关键失败步骤和9类错误，实验用GPT-5作为默认诊断模型，报告与这些人工标签相符的准确率。τ-bench的29条上，最佳一次生成约束设置把严格步骤匹配率从基线32.2%提高到54.0%，类别准确率从25.3%提高到40.2%；这些是三次运行的结果统计，而不是115条都达到同样幅度。逐步生成在该组反而较弱，长轨迹上的趋势又不同。证据支持“检查日志能帮助归因”，也显示诊断离可靠自动判定尚远，不能用最佳一组结果概括所有场景。[数据与表5、第4.6节](https://arxiv.org/html/2602.02475v1)

证据限制：约束含模型语义判断，不等于机械证明。115条失败轨迹中的子集结果不可概括全部场景；关键未恢复失败与首次状态分歧是不同标签。

阅读建议：第3节、表5、附录B；结合方法、结果和限制阅读。

## 4. Scaling Agentic Data for Long-Horizon Terminal Intelligence

来源：[原始页面](https://arxiv.org/abs/2610.13166) · [全文入口](https://arxiv.org/html/2610.13166v1)；Shun Zou; Ziyu Ma; Yi Zou; Yong Wang; Lin Chen; Zehui Chen; Guanhua Chen; Xiangxiang Chu; Feng Zhao；首发 2026-10-09，核查版本 v1。

这篇论文研究终端任务合成，问题并不是调用太少，而是生成环境时可能已经把应留给agent的工作做完了。任务文字要求探索、实现和验证，初始文件却可能带着几乎完成的解法；执行轨迹于是很短，即使把说明写复杂，也未必真的出现持续解决问题的过程。作者提出TerminalHorizon，用独立执行发现这种任务构造中的捷径，再修整环境，随后沿同一目标增加依赖前一阶段结果的新要求。

每个任务包包括公开指令、可执行环境、参考解、私有验证器和执行配置；执行agent只看到公开指令和环境。第一阶段先从专业问题构造任务，再让没有参与构造的agent尝试解决。系统分析轨迹中是否出现预期的探索、诊断、实现、验证等行为，检查材料是否提前提供答案、是否简化了必要工作，并据此重建任务环境。第二阶段不是机械追加无关子题，而是使新要求依赖已有结果及反馈：早先的方法可能需要改进，后续验证也可能要求返回修正。这里的“重建”是编辑任务初始环境来保留工作量，而不是从黑盒响应复现某个固定服务的语义。[第2节、图2](https://arxiv.org/html/2610.13166v1)

作者生成1,535个任务环境、收集2,852条训练轨迹，平均每条52.8个交互轮次，再对Qwen3.5-27B做监督微调。报告覆盖12组benchmark；附录说明基础模型和微调模型在各组采用同一任务集、agent框架、解码设置和评分流程。Terminal-Bench 2.1的89个任务上，每任务独立运行3次、允许agent最多3小时，作者报告平均pass@1从46.82%提高至60.67%，增加13.85个百分点。通过与否由任务验证器判定，不是轨迹行为分析器直接打出的质量分。这个比较支持整套数据训练后有迁移收益，但没有把“独立执行修整”与“渐进扩展”的贡献完全拆开；更长轨迹本身也不等于更准确的环境。[主实验表2及附录A.2](https://arxiv.org/html/2610.13166v1)

证据限制：整套数据训练的效果未完全拆分环境修整与渐进扩展；长轨迹不等于保真。终端执行与任务验证器证据不能改写为真实外部服务模拟器已通过差分验证。

阅读建议：第2.1—2.3节、图2；结合方法、结果和限制阅读。

## 5. Dream-RSI: Recursive Self-Improvement through Evolving Worlds

来源：[原始页面](https://arxiv.org/abs/2609.14858) · [全文入口](https://arxiv.org/html/2609.14858v1)；Tong Zheng; Xidong Wu; Zheng Zhang; Zhankui He; Chaoyi Zhang; Benjamin Coleman; Ruoqiao Wei; Di Bai; Haolin Liu; Rui Liu; Xue Wang; Yue Zhuan; Wang-Cheng Kang; Renkai Xiang; Heng Huang; Xinwu Cheng; Yunsong Guo；首发 2026-09-14，核查版本 v1。

科学发现agent反复生成程序、运行评测，每轮都很昂贵，但已跑过的搜索历史往往只被写成文字经验。Dream-RSI试图把历史变成可重放的环境，让系统先便宜地比较不同探索策略，再去执行新的真实搜索。它主要改进的是“从哪条分支继续、并行尝试多少条、何时停止”的调度策略，底层写程序的agent和任务评测器仍承担候选生成及正确性检查；不是把整个真实环境交给模型随意想象。

在线搜索保存一棵树，每个节点是一轮尝试的工作区、产物、评测诊断和分数。策略可以选择根节点开启新分支，或从当前观察树的叶节点继续；每批选择数受并行工作数限制。真实执行会生成并评测新候选，再把结果加成子节点。离线改策略时，历史树固定不变，从只有根节点的观察状态重新开始：选一条已有分支，就返回它记录中的后续节点；选根节点，则按记录顺序揭示尚未显示的分支；没有记录的延续返回空集合。由此能比较访问顺序、分支选择和停止时机，但不能回答历史之外任意新程序会取得什么结果。改进后的策略再部署在线，增加新历史，形成下一轮重放依据。[第3节](https://arxiv.org/html/2609.14858v1)

作者在8个科学发现任务上实验，覆盖算法、数学优化和GPU核函数。较有解释力的是与Recursive Fixed Exploration的控制比较：保持底层发现设置、初始化与每轮预算一致，第一轮策略相同，后续一方保持调度不变，另一方通过重放修改策略。GPU实验采用Gemini-3.1 Pro，在4个KernelBench任务上先检查候选相对参考实现的正确性，再比较运行时间的倒数。作者报告VGG16和LayerNorm达到可比运行性能时，所需候选生成次数分别减少约2.43倍和1.79倍。这里测的是搜索调用节省，不能理解为端到端费用同比下降：离线修改策略、存储与重放本身仍有开销。与不同系统的巨大倍数也没有这组同设置比较那么直接。[第4节、图4](https://arxiv.org/html/2609.14858v1)

证据限制：重放只支持已记录分支；缺失延续返回空集合，不能泛化到任意新候选。生成次数节省未包含所有离线策略改写、存储与重放成本。

阅读建议：第3节Online rollout与Offline evaluation、图4；结合方法、结果和限制阅读。
