## 1. From Dead Code and Static Requirements to Working Engines: Software Revival with Coding Agents

[原始来源](https://arxiv.org/abs/2609.36161) · [正文](https://arxiv.org/html/2609.36161v1)

首发：2026-09-28 · 预印本v1

这篇研究两种容易混在一起的软件任务：把已经不能运行的旧软件修好，以及看不到原实现、只凭公开规格重新实现一个引擎。前者有旧代码，难点是依赖、构建和被删模块；后者要自己写出行为。其中第二部分包括13个有边界的引擎重建任务，涵盖数值、几何、硬件和事务系统。作者给模型规格与三个演示例子，禁止安装任务列明的现有实现，再用模型看不到的评分程序验收。因此，它并非任意闭源服务的完整克隆，而是明确语义范围内的实现任务。

评分依据随对象变化。数值计算与认证值或成熟工程软件比较，硬件结果可以检查形式等价，事务系统则检查账务及状态约束。参考对象包括原生运行环境、外部工具和专门编写的参考实现。这样的设计把“程序能运行”推进到“结果满足外部语义”，但也把很大的可信度押在评分资产上。作者报告两个模型达到全部13项任务的通过门槛；这不是每个检查均正确的保证，多数实验单元只有一到两次尝试，矩阵还选取合规运行中的最好结果，不能据此推断稳定通过概率。

最有信息量的是评分器审计。作者累计找到28处缺陷，其中24处会错拒正确实现、两处会错收错误实现，这些是构建审计中的缺陷数，不是模型错误率。例如，计算流体任务原本使用候选程序自己上报的诊断量评分，一个没有网格、直接计算规格中解析式的小程序也能过关。作者据此撤回“分数证明实现了真实数值求解器”的解释。另一项检查是按规格指定路线亲自算出答案，确认容差确实可达；多个候选一致而参考值不一致时，也回查规格和评分路径，而不直接宣布模型错了。

**证据限制：** 13项任务的最佳合规运行不能推断稳定通过概率；评分器缺陷数不是模型错误率，自报诊断不证明数值求解器成立。

**先读：** 第3节、第8节及图3。

## 2. VeriEvolve: Evaluator-First Evolution for Tool-Using Agents

[原始来源](https://arxiv.org/abs/2610.29005) · [正文](https://arxiv.org/html/2610.29005v1)

首发：2026-10-21 · 预印本v1

VeriEvolve关心的是：如果工具代理的成功标准不可靠，搜索出“更会得高分”的工作流可能只是在利用评分漏洞。作者把顺序改为先构建可执行评测器，再用它优化代理。输入包含用户指令、初始世界和只读观测接口；只有成功与否能由该接口观察到的任务才适用。系统先生成应该成功、明显失败及带有迷惑性的状态描述，由确定性适配器在隔离环境中实例化，再生成读取这些状态、输出判断和证据的评测程序。

评测器在一轮代理搜索中保持冻结。代理工作流由理解、规划、工具行动、检查和后处理等节点组成，搜索会替换节点候选。轮次之间，作者用可靠成功状态与“内部评分成功、外部判断失败”的状态比较，寻找与指令有关的差异，再生成只改变关键因素的成对测试。新版评测器要保留既有正确判断并排除先前漏过的错误，才进入下一轮。论文中的目录镜像任务很具体：旧评测器只检查八个空叶目录中的五个，弱代理漏建剩余目录仍获成功；状态对照把这类遗漏转成新的测试条件。

关键条件是，外部真值没有消失。作者没有把基准验证器源码或判决直接作为模型优化反馈，但外部标签仍用于筛选评测器、认证成功参考，以及发现触发修订的假阳性。因此，把它概括成“无需参考验证器的自我验证”会误导。作者在构造阶段用141个挑战状态检查评测器；另取122个留出的代理产出状态，与外部验证器比较，有113个一致，其中三次错收、六次错拒。这组状态来自搜索过程，偏向内部高分候选，说明的是该分布上的判断能力，不是所有可能服务状态上的正确率。

**证据限制：** 外部验证标签仍参与评测器筛选与修订；122个留出状态偏向内部高分候选，不能推广到所有服务状态。

**先读：** 第4.3节、图2与表2。

## 3. CRM-Agent-Bench: Benchmarking Tool-Using Agents in Stateful Enterprise Environments

[原始来源](https://arxiv.org/abs/2610.32004) · [正文](https://arxiv.org/html/2610.32004v1)

首发：2026-10-23 · 预印本v1

CRM-Agent-Bench针对企业代理中“回答得像完成了，实际账务却错了”的问题。它构造九类业务领域的555个多轮任务，环境中的记录会被工具调用持续修改。每次试验从规定状态重新开始，代理只能看到工具说明与返回结果，看不到原始状态和隐藏验收合同；模拟用户依据私人目标与代理可见回复继续对话。这里评测的是整个代理系统完成业务的能力，环境是合成的可控CRM，并非直接连接真实厂商生产服务。

每个任务带有自己声明的一组可执行要求：可能包括必须成功执行的调用、参数、先后顺序、回复内容、目标状态，以及不得触碰的动作或受保护状态。任务成功要求已声明的检查全部通过，未声明的维度不会被偷偷算成通过。成功调用与禁止尝试还分开记录：前者要求实际执行成功，后者可以把被工具拒绝的尝试也计入违规。回复检查可以由语言模型完成，但它不能覆盖程序检查发现的状态错误。延迟和费用另外报告，不与业务成功混成一个分数。

论文里的重复结账案例解释了为什么要这样做。代理面对15.50美元的结账操作，回复、调用类别和顺序看起来都合格，却执行了两次，会员积分余额变成310而非应有的155；如果只看对话，容易宣布成功，检查持久状态才发现重复执行的后果。作者在最终版本上评估16个系统，每个完整覆盖555项，严格成功率范围为64.32%—83.60%。这些是作者参考代理结构及合成任务下的结果，不是线上CRM可靠性。后续重复运行还观察到总分相近时具体任务结果会翻转，因此只比较一次总分可能掩盖不同的失效位置。

**证据限制：** 作者定义的业务合同不等于厂商固定版本行为；合成CRM结果不是生产服务可靠性。

**先读：** 第2.3节及附录D。

## 4. AgentEval: Evidence-Bounded Assessment of Stateful Agents

[原始来源](https://arxiv.org/abs/2610.21177) · [正文](https://arxiv.org/html/2610.21177v1)

首发：2026-10-15 · 预印本v1

AgentEval把三个问题拆开：代理当时做了什么，保留下来的证据能够证明什么，以及这些证据现在还能否用于报告。一次退款可能确实发生过，但若状态快照丢失，就不能靠同一条“成功”记录重新证明它；反过来，证据缺失也不会改变过去已经发生的行为。系统把任务合同、运行条件、初末状态、事件、检查结果及版本身份绑定为一份评估记录，报告复用时重新检查这些绑定，而不改写历史判决。

它保留成功、违反要求与无法确定的区别。论文中，某些文档创建任务必须先取得可信请求者的澄清答复；代理已经询问却没有收到绑定的答复时，合同中的相关义务无法确定，这不等于文档已创建。权限案例也很有启发：代理先请求用错误身份处理工单，工具拒绝且状态不变，随后以正确身份成功完成。若合同约束的是持久状态，第一次提议不能直接当作已提交写入；是否另外处罚禁止尝试，则取决于合同声明。这一点与CRM的计分选择不同，并不矛盾。

作者尝试了32次工具世界运行，30次完整结束、两次因预算键幂等冲突中断，原样保留在分配记录中。独立检查与系统在30个完整运行上的标签一致，其中23个成功、两个失败、五个无法确定；这不是32次全成功，也不是广泛任务上的准确率估计。作者还对48份证据视图进行编辑与恢复，36份编辑后的视图能骗过只检查内容哈希的办法，因为文件字节仍一致，绑定的规格、种子或评估身份却已经错位。这是证据视图实验，不是额外48次代理运行。

**证据限制：** 30个完整运行不能代替32次分配；48份证据编辑不是48次代理运行，哈希一致不能保证上下文绑定正确。

**先读：** 第3—4节及第6.2—6.4节。

## 5. Behavioral Regression Detection for Pull Requests via Structured Oracles

[原始来源](https://arxiv.org/abs/2610.35223) · [正文](https://arxiv.org/html/2610.35223v1)

首发：2026-10-26 · 预印本v1

ORION检测代码修改是否破坏原本正常的行为。只让模型看差异生成测试，容易把注意力全部放在新增功能，却漏掉应该保持的老用法。作者因此先写一层结构化行为要求，明确哪些行为必须保留、哪些是有意改变，并附带运行前提和关键分支条件，然后才生成测试。它可以同时访问修改前后源码、提交说明和函数关系，这种资料条件比黑盒服务重建充分得多。

系统先用抽象语法树定位受影响函数，提取参数删除、默认值变化、异常变化等风险，再让模型生成上述行为要求。测试生成器据此构造可执行案例，对遗漏要求补充测试，并修复静态执行问题。同一测试在依赖和资源配置一致的前后版本中分别运行，记录异常、返回值与运行状态；先用规则处理明确情况，再让模型结合预期变化回答受约束的判断问题。部署失败不会直接成为回归证据，只有基础设施错误的提交会另外标记供人工检查。

论文用yt-dlp的一个修复说明问题：修改本想跳过失效的视频嵌入，却把带有特殊引用信息的地址交给普通网页请求器，导致原本可用的嵌入也失败。若只测“坏地址能否绕过”，看不到这个错误；把“有效嵌入仍须成功”写进保留要求，便能生成修改前通过、修改后失败的案例。作者在77个回归与77个非回归提交上评估，DeepSeek后端的F1为0.6125，高于同后端Testora的0.3243；F1衡量检出率与查准率的平衡，不是61.25%的提交完全判对。与PatchGuru在共同完成的单函数子集上比较则没有稳定优势，不能把全量结果写成对所有方法的全面胜出。

**证据限制：** 源码和变更意图是额外信息；154个平衡样本上的F1不是逐提交准确率，与PatchGuru比较无稳定优势。

**先读：** 第II节、第III-B/D节及表I、III。
