## 1. Automated Synthesis of Cloud Emulators

来源：[原始页面](https://arxiv.org/abs/2608.23842) · [全文入口](https://arxiv.org/html/2608.23842v1)；Archit Bhatnagar; Zhenning Yang; Sarah McClure; Yiming Qiu; Sylvia Ratnasamy; Ang Chen；首发 2026-08-24，核查版本 v1。

CloudEmu 想解决的是云模拟器维护追不上真实服务的问题。手工实现需要读大量文档，也容易漏掉资源之间的约束；直接让模型把文档变成代码，又容易遗漏接口，或者把创建、查询、删除写成各自独立的函数。作者改变的是模拟器生成的组织方式：先按资源整理文档，再在统一的状态机框架中生成接口行为，最后以真实云调用的差异修正代码。这里的状态机不是只记录“成功或失败”，而是维护资源及其关系，让后续调用看见此前操作造成的变化。[原文第2—3节](https://arxiv.org/html/2608.23842v1#S3)

具体流程从文档的结构索引开始，选取某个接口所需的片段和关联资源信息，而非每次塞入全部文档。生成的代码接入已有框架；随后，系统用符号执行寻找代码路径及其条件，再让模型构造可执行的 CLI 或 Terraform 调用序列。序列分别在模拟器和参考云上运行，比较错误、返回字段以及中间状态。资源 ID、时间戳等变化字段需要归一化；出现连续差异时先定位最早的不一致，避免把同一个根因算成多次错误。修复既包含缺字段等机械修改，也包含针对局部代码的模型补丁，再通过重跑检查。论文举出的删除仍有关联资源的子网等情形，说明约束必须作用于跨接口状态，而非仅修改返回文本。

作者把真实 AWS 作为参照，在50个 CLI、50个 Terraform 用例上比较 CloudEmu 与 LocalStack，并说明对齐没有使用这批测试用例。三个保真层次逐步要求错误码一致、关键返回字段一致、以及中间状态一致；一条用例中全部调用满足要求才算通过。作者报告各层次均优于 LocalStack，但这是一组被抽取的用例，不能把其中覆盖良好解释成所有 EC2 输入都已验证。另一个330用例的消融实验以 LocalStack 作参照，因此它说明设计对该参照的拟合收益，不能替代真实 AWS 的保真证据；两种实验必须分开读。[原文第4节](https://arxiv.org/html/2608.23842v1#S4)

证据限制：抽样用例不覆盖全部EC2输入；约1.24万行专用框架带有人工作业成本。真实AWS保真证据与LocalStack拟合消融应分开。

阅读建议：第3.3、4.1—4.3节；结合方法、结果及限制阅读。

## 2. Fidelity of Cloud Emulators: The Imitation Game of Testing Cloud-based Software

来源：[原始页面](https://doi.org/10.1109/ICSE55347.2025.00077) · [全文入口](https://tianyin.github.io/pub/cloudtest.pdf)；Anna Mazhar; Saad Sher Alam; William X. Zheng; Yinfang Chen; Suman Nath; Tianyin Xu；首发 2025-04，核查版本 ICSE 2025。

这篇研究从使用者的测试结果反问：一个模拟器即使实现了接口，是否足以让开发者相信本地测试？作者调查 Azure 的 Azurite 和 AWS 的 LocalStack，选择 Blob、Queue、Table、S3、DynamoDB 五项服务。他们关注的不是文字响应相似度，而是相同软件放在模拟服务和真实服务上，会不会得出不同的测试结论。模拟器放过真实服务会拒绝的调用，可能导致上线失败；模拟器拒绝真实服务能执行的调用，则会制造误报。[原文第I—III节](https://tianyin.github.io/pub/cloudtest.pdf)

作者采用两类输入。第一类是依据接口约束变异参数的 SDK 调用序列：先创建后续调用需要的资源，观察返回结果，再决定能否继续。选 SDK 而非任意原始 HTTP 请求，是因为 SDK 自带检查，许多底层非法输入根本不会被实际应用发出。第二类来自十个现有开源项目的测试，用来检查差异是否真的影响应用。两边独立执行同一序列，除响应和错误信息外，还检查调用前后的关键对象，例如 blob 数量；后者能发现响应看起来正常但留下资源的差异。发现后再复现并定位模拟器源码中的原因，而不是把任何一次不同都立即当成确定问题。

在这五项服务的255个 API 中，作者发现94个至少存在可触发的行为差异，即37%。分母是接口数量，不是调用次数；这个数字不表示每次请求有37%概率出错，也不是今天最新版模拟器的测量。研究进一步展示这些差异如何造成不同应用测试结果。作者提出的 ET 工具并不尝试马上修好所有模拟器，而是选择哪些完整测试应回到真实云执行：可以依据已知有差异的 API，也可以记录已在云上核过的调用序列，只有请求、响应和顺序都符合已有安全记录时才省掉云重跑。未知序列仍需核验；论文特别解释，不能随意在一条测试中切换两种后端，因为同步状态代价高。[原文第IV、VII节](https://tianyin.github.io/pub/cloudtest.pdf)

证据限制：比例分母为接口，非每次请求的错误概率；研究版本及工作负载有限。已验证调用序列的复用不证明新组合安全。

阅读建议：第III、IV、VII节；结合方法、结果及限制阅读。

## 3. Toward Interactive Understanding of Code APIs

来源：[原始页面](https://arxiv.org/abs/2609.32081) · [全文入口](https://arxiv.org/html/2609.32081v1)；Dhananjay Ashok; Jesse Thomason; Jonathan May；首发 2026-09-25，核查版本 v1。

PAU 研究一个常被默认成容易的问题：不给源代码，只允许查询输入输出，模型能否理解一个函数在做什么？作者从代码基准中整理训练集和741个测试实例，把函数及参数改为没有语义提示的名字。每题给函数声明和两个有效输入输出例子；模型可以追加黑盒调用，最终写一段功能描述。所有函数都不保留调用之间的状态，因此它隔离了“从行为发现规则”这一困难，没有覆盖服务的历史依赖。[原文第2节](https://arxiv.org/html/2609.32081v1#S2)

交互被拆成可观察的过程。模型先根据当前假设考虑下一次输入应检验什么，再生成具体 Python 参数元组；执行器返回结果或异常，模型据此更新假设，也可以决定已经理解并停止。最多允许25次 API 调用。这样可以区分“不会调用”与“调用了却没有纠正解释”。论文错误分析发现，部分最终描述甚至和模型已经获得的输出矛盾；另一些模型倾向于重复普通输入，或过早认为证据充分。作者尝试加入边界输入和对比查询等提示，但不能仅凭这种提示就消除问题。

评判有两条路径：Llama3-70B 根据真实功能给描述打1—5分；另一条用 Qwen3-Coder-30B-A3B 将描述转回代码，再统计测试输入上的输出一致率。作者报告，Claude-4-Opus 在超过45%的测试函数上描述得分不高于2；按描述重写的代码也在超过45%的函数上达不到80%的输出一致率。这两个比例都以测试函数为单位。更关键的是，给代码生成器正确描述时，平均输出一致率仍只有约72.96%，所以后一个指标包含重写模型的误差，不能全归因于探测者。测试的平均语句和分支覆盖超过99%，也不能保证已穷尽所有语义输入。[原文第2—4节及附录C](https://arxiv.org/html/2609.32081v1)

证据限制：重写指标包含代码生成误差；结构覆盖不等于语义穷尽。正文模型名和显著性图注有不一致，不能推导完整排名；无跨调用状态。

阅读建议：第2节、图2—3、附录C；结合方法、结果及限制阅读。

## 4. Push-Button Reliability Testing for Cloud-Backed Applications with Rainmaker

来源：[原始页面](https://www.usenix.org/conference/nsdi23/presentation/chen-yinfang) · [全文入口](https://www.usenix.org/system/files/nsdi23-chen-yinfang.pdf)；Yinfang Chen; Xudong Sun; Suman Nath; Ze Yang; Tianyin Xu；首发 2023-04，核查版本 NSDI 2023。

Rainmaker 讨论的是云应用面对短暂故障时的正确性。一个容易忽略的区别是：请求没到达服务，与服务已经写入但响应丢失，都可能让调用方看到“失败”，却要求完全不同的恢复动作。单纯随机塞入错误码容易错过这种区别，甚至制造不符合服务契约的故障。作者依据真实错误模式设计少量明确的注入策略，让现有应用测试能够覆盖重试和状态分歧，而无需开发者逐个编写新的故障用例。[会议页面](https://www.usenix.org/conference/nsdi23/presentation/chen-yinfang)

工具在应用与云之间放一个 HTTP 代理，识别同一次 SDK 调用及其重试。它可以让第一次响应超时、让全部响应超时、阻止所有请求并返回暂时错误，或让第一次写入成功但响应超时，再对重试返回暂时错误。后两种情况下，调用方最终都可能报失败，远端状态却分别是未执行和执行过一次。论文中 BotBuilder 的例子很直观：创建 blob 已经成功，响应丢失触发 SDK 重试，第二次收到“已经存在”；错误处理终止了日志循环，后续日志丢失。这是作者展示的实际缺陷。

代理并非在所有请求上穷举故障，而是结合应用调用位置和已有测试选择注入点，以减少大量重复执行。执行后利用测试结果和工具的错误检查判断潜在问题。正式论文在11个使用云服务的 .NET 应用中报告73个新发现，其中55个被确认、51个已修复；这些数量并不意味着每个告警都已经确认，也不是73种独立云服务故障。微软页面仍保留44确认、40修复的较旧统计，本报告采用 USENIX 正文的数字。论文证明选定策略能揭露有实际后果的应用缺陷，未证明它覆盖所有故障或所有语言客户端。[正式论文第3—5节](https://www.usenix.org/system/files/nsdi23-chen-yinfang.pdf)

证据限制：未证明覆盖全部故障及语言客户端；旧微软页面44/40与正式论文不同。研究真实应用故障注入，非生成模拟器。

## 5. Benchmarking Combinations of Learning and Testing Algorithms for Automata Learning

来源：[原始页面](https://doi.org/10.1145/3605360) · [全文入口](https://tugraz.elsevierpure.com/ws/portalfiles/portal/77962395/3605360.pdf)；Bernhard K. Aichernig; Martin Tappler; Felix Wallner；首发 未知，核查版本 Formal Aspects of Computing 36(1), article 3。

这篇自动机学习研究关心如何用更少的黑盒测试恢复一个系统的行为模型。这里的模型把每个状态、输入动作和输出连接起来；同一输入在不同历史之后可以产生不同输出。学习器根据观察建立暂时模型，测试器则主动寻找模型与真实对象不一致的序列。找到反例后再修订模型，循环进行。作者强调，两类调用承担不同责任：一类获取构建模型所需的信息，一类检验当前模型是否仍有错误，选择方式会相互影响。[论文第1节](https://tugraz.elsevierpure.com/ws/portalfiles/portal/77962395/3605360.pdf)

论文比较六种学习方法与七种测试方法。随机测试选动作序列；状态覆盖测试优先经过当前模型的不同转移；变异测试先构造可能的错误模型，再选择能区分这些模型的序列。随机 Wp 方法则从结构化的一致性测试中抽取部分用例：序列用于到达状态、经历额外动作并区分后续状态，比完全随机游走更有目的性。完整的一致性测试在已知状态数上界等前提下有形式保证，但随机抽样版本不保留这种保证；这是论文明确区分的两件事。

实验对象是153个已有行为模型，包括 TCP、MQTT、TLS 等，而非向真实线上服务收费探测。作者搜索使十次重复学习都正确的最低测试预算，再用执行的输入步数比较组合，不只数整条测试。所有组合共同完成的116个对象与包含困难对象的153个集合分开呈现，后者对未完成情况施加惩罚。随机 Wp 总体表现较好，变异方法在较小模型上有优势；部分方法还受12 GB内存及实现限制。因而“最好”依赖对象集合、参数与失败处理，不是可以直接移植到任何 API 的固定排名。[论文第4、6节](https://tugraz.elsevierpure.com/ws/portalfiles/portal/77962395/3605360.pdf)

证据限制：随机Wp抽样没有完整一致性测试的形式保证；模型集合、失败惩罚、12GB内存及实现限制影响比较。无限数据参数及异步行为需要额外抽象。 2024-03为所核期刊卷期，在线首发日期未单独核实。

阅读建议：第4.1.4节、图6—7；结合方法、结果及限制阅读。
