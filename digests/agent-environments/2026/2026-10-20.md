## 1. EnvFactory: Scaling Tool-Use Agents via Executable Environments Synthesis and Robust RL

[原文](https://arxiv.org/abs/2605.18703) · [正文](https://arxiv.org/html/2605.18703v1) · 2026-05-18 · v1 · preprint

这篇论文要解决的是工具使用训练缺少足够多、足够可靠的交互环境。直接接真实服务，调用成本、权限和重置都难管理；让语言模型临时扮演服务，又可能出现返回值看似合理、内部状态却前后矛盾的问题。作者因此把环境做成能实际运行的 Python 程序，向智能体暴露 MCP 工具接口，并用明确的数据模型保存状态。它主要服务于训练数据和强化学习环境的扩展，不是从一个固定服务的观测中恢复其全部行为。

环境生成有具体的资料和代码过程。搜索智能体根据已有环境的覆盖缺口寻找在线文档、报告和示例，形成服务规格；代码智能体据此定义状态实体、序列化和恢复方式，编写工具的实现。测试智能体检查接口是否符合规格、代码能否导入和执行、输出是否符合预期，以及调用后数据库状态有没有正确更新；失败报告会交回代码智能体修复，直到通过或耗尽预算。这里的状态数据库不是供模型自由叙述的背景文字，而是代码读取和修改的对象，因此一次写入能在后续读取中留下可检查的结果。

为了从这些环境产生有意义的多步任务，作者还分析工具之间的依赖：先用输入输出语义和嵌入相似度找候选边，再由模型细化隐含联系。生成调用链时递归补齐前提，而不是简单随机游走，避免某个工具需要多个先决条件时只满足其中一个。论文举出的无参数“删除所有笔记”这类操作，也说明依赖不能只靠参数名字匹配。随后生成用户目标和交互数据，进入监督训练及强化学习。

作者报告构建了85个环境，覆盖7个领域，产生1,622段监督训练对话和953个强化学习任务。在 Qwen3-4B 上，BFCL 多轮部分的基准准确率由基础模型的33.50%升到完整流程的48.50%；MCPAtlas 的任务通过率由4.12%升到9.97%。这些是训练后智能体在外部任务上的表现，由相应基准评分；分母是各自的评测任务集合，不是生成环境中的接口数，也不是环境忠实度。不同环境生成方案还使用不同数量的数据，因此跨方案分数不能直接解释成同预算下某个生成组件的净效果。

**证据限制：**环境自检及下游训练收益不能替代独立参考服务行为保真；生成方案数据量不同，非同预算组件对照。

## 2. Generating Mock Skeletons for Lightweight Web-Service Testing with Description Logic Learning

[原文](https://link.springer.com/article/10.1007/s11761-026-00495-w) · [正文](https://link.springer.com/article/10.1007/s11761-026-00495-w) · 2026-05-22 · published fulltext · journal_article

如果只有 HTTP 请求与响应记录，能否自动学出一个轻量替身，减少手写 mock 的工作？这篇论文选择了可解释的符号规则，而不是直接训练一个黑盒响应生成器。作者称输出为“骨架”，这个用词很关键：它学习的是哪些请求条件与哪些响应字段取值相关，并没有声称恢复出完整的业务数据库和服务实现。

方法先把一次 HTTP 事务表示成知识图谱中的对象，请求方法、请求属性、响应属性等都转成可查询的关系。为了让模型看到历史，它为同一资源建立指向紧邻前一次事务的 hasPrevious 关系，以及覆盖更早历史的 isPrecededBy 关系。这样，规则不仅能表达“这是某类请求”，还可以表达“当前请求之前发生过某类请求”。面对新样本时，要预测的响应信息被移除，学习器根据剩余请求和历史关系推断它。

具体学习时，某个响应属性的一个取值被当作二分类目标，描述逻辑学习器 OCEL 从很宽的概念逐步加条件，寻找能区分正负样本的规则。其结果是人能检查的逻辑表达式，而不是完整响应对象的联合生成程序。作者在试运行后为每个目标设置120秒上限；知识表示的内存开销使部分数据只能抽样，原本更高折数的验证也因内存问题改成两折。无正例或无负例的类别没有进入同样的学习评测，因此结果不能自然推广到全部响应值。

实验使用 GitHub 的 GHTraffic 数据，以及经 OpenAPI 模糊测试取得的 Twitter、Google Tasks、Slack 数据，不能统称为不加干预的生产日志。作者汇总的准确率看起来很高，约为0.9216至0.9941，但更有信息的是少数错误分支：Google Tasks 的503响应类别只有2个正例、1,122个负例，表中两折评测的准确率仍达0.9893，精确率和召回率却都是0。也就是说，“总体大多猜对”可以与“一个稀有分支都识别不到”同时成立。这些是论文报告的交叉验证指标，不能把它们直接换算成部署后的错误发生率。

**证据限制：**响应字段二分类不等于共享状态执行；部分样本抽样、两折验证；稀有失败类别可能完全漏识别。

**建议先读：**5.2历史表示；第6节503结果

## 3. Gaia2: Benchmarking LLM Agents on Dynamic and Asynchronous Environments

[原文](https://arxiv.org/abs/2602.11964) · [正文](https://arxiv.org/html/2602.11964v1) · 2026-02-12 · v1; original page states ICLR 2026 Oral · preprint_with_acceptance_note

很多工具评测默认环境会等智能体：模型想多久都不改变任务世界，外部事件只在固定调用点出现。Gaia2 要考察的是另一种情况：通知持续到来，新的信息可能使原计划失效，动作还可能有时间要求。作者在包含12类应用、101个工具的环境中设置任务，让智能体在持续变化的状态里工作。它评测的是执行任务的智能体，而不是生成服务替身的方法。

一个场景由初始数据、事件时间线和验证条件组成。事件可以按绝对时间发生，也可以依赖先前事件形成有向无环图；应用工具读写共享数据，通知策略决定智能体何时看到变化。模型生成文本期间时间也会前进，因此一次看似正确、却作出太晚的操作可能失败。论文还讨论在重放和运行中处理生成延迟等因素，使场景的事件推进与智能体实际耗时相联系。这里“异步”不是多加几个工具名称，而是观测、决策和外部变化不再被同一个固定轮次锁住。

评分器也没有只问模型一句“任务做完了吗”。作者为任务提供最小必要写操作的参考路径，检查依赖、时间约束和完成情况，同时允许额外的读取探索及部分互不依赖写操作的不同顺序。对象标识等条件可以精确检查，自由文本内容则仍需要语言模型依据规则判断。这种组合把可以机械检查的部分固定下来，也保留了对表达方式的容忍。

作者用450条人工标注的验证轨迹检查评分器，报告其与人工判断的一致率为0.98，而仅用语言模型判断的方案为0.72。这一比较支持“结构化动作条件能改善这里的任务评分”，但它验证的对象是轨迹是否完成场景目标，并非环境模拟器的响应是否与真实服务相同。实验中的模型采用共同的 ReAct 交互框架；因此结果应放在该任务、框架与时间机制下理解，不能单凭排名推断所有异步服务中的能力。

**证据限制：**验证450条轨迹的任务完成判定，而非模拟器对真实服务的保真；自由文本仍使用模型评分。

**建议先读：**第4节和表1，再读第3节

## 4. Automated REST API Black-box Test Generation in Practice: An Experience Report from Industry

[原文](https://orbilu.uni.lu/handle/10993/68146) · [正文](https://orbilu.uni.lu/bitstream/10993/68146/1/ICST-2026-REST-test-generation-in-practice.pdf) · 2026-07 · author postprint; ICST 2026 institutional record; institutional deposit 2026-04-03, first online date unknown · conference_paper

这篇工业经验报告关心一个实在的问题：自动 REST API 测试工具离开公开小系统后，能否在真实企业接口中探索有效操作、发现故障？研究比较 RestTestGen 和 DeepREST，在5个工业 API、共204个操作上运行。对象涉及不同实现语言，测试环境采用接近生产的数据快照，而不是每次都从几乎空白的数据库开始。

RestTestGen 依据 OpenAPI 描述组织调用依赖，生成正常及异常输入，再检查响应约束和服务器错误。DeepREST 用强化学习引导探索，并利用语言模型帮助准备参数值。企业环境的安全约束使作者不能在线调用外部模型，所以实际使用本地 Qwen3-14B 预先生成并缓存输入字典；这里的语言模型并没有在每一步看到服务反馈后现场推理。这个条件会影响我们怎样理解“用了大模型”带来的收益。

预算设计尤其值得看。每个工具在每个 API 上独立运行10次，每次允许的 HTTP 请求数为该 API 操作数的200倍；五个 API 合计，每轮对应40,800次请求。每次独立运行之前恢复数据库快照。因此比较约束的是请求数量，而不是让响应快的系统在相同时长里多发请求。重置也给出了清楚的起点，否则早一次运行留下的数据会改变后续可达路径。论文的操作覆盖指标要求一个操作至少产生过一次2XX响应；它衡量成功触达接口，不能解释成分支覆盖或状态转换覆盖。

按各 API 运行结果的中位数汇总，两工具都成功覆盖151/204个操作，约74%；故障数中位数汇总分别为17和18，最佳运行的汇总分别达到20和21。故障通过服务器错误及错误信息聚类等方式识别，并由开发者核查；其数量受聚类准则影响，不等于21种完整业务语义已被系统地验证。文章也指出 multipart 输入支持不足、规格里缺少领域信息等障碍，这些会阻止工具进入某些操作。探索失败因此既可能来自服务前提难满足，也可能只是测试生成器不支持相应输入格式。

**证据限制：**2026-04-03仅为机构库入库日；论文集为2026年7月，首次在线日未确立。真实API测试非服务仿真；操作覆盖不等于分支或状态覆盖。

**建议先读：**V-A/B、表III；VI-B

## 5. Four evaluation engineering lessons learned from building agent plugins

[原文](https://cloud.google.com/blog/topics/developers-practitioners/four-eval-engineering-lessons/) · [正文](https://cloud.google.com/blog/topics/developers-practitioners/four-eval-engineering-lessons/) · 2026-10-16 · official article dated 2026-10-16 · official_technical_article

这篇文章从插件开发中的误判出发：智能体的最终回答看起来不合要求，到底是模型不会做，还是评测器没看到它已经做过的事？作者最初用11条提示组成小规模评测，其中3个失败后来被确认是误判。一个例子是要求先查看命令帮助，最终回答里没有写出这个过程，评分器便判它遗漏；原始工具记录却显示它已经调用过 gcloud 的帮助。这里能支持的是具体评分规则出了错，不能把这组开发案例当成普遍误判率。

第二个案例更贴近交互环境。在同一个模型回合中，智能体同时发出加载技能和两次文档搜索；技能正文要等工具返回后才能进入下一轮上下文，因此两次搜索发生时，模型还没看到新加载的指令。如果把日志压成一个线性文本列表，就很容易误读成“先加载并读懂规则，接着故意违反规则”。作者据此强调保留原始调用批次和上下文边界：工具调用在日志中的排列次序，并不自动意味着前一个工具结果已经被后一个决策观察到。

文章还区分有真实凭据、允许执行的环境与只能给计划的环境。凭据或权限失败可能盖住本来想测试的推理行为；专家认可的样例则应固化成回归集，用来检查模型、工具和评测框架的变化。作者给出这些工程经验，但没有统一控制条件和大样本对照，因此它的价值在于揭示可复查的失败机制，而不是证明某种评测架构普遍更优。

**证据限制：**官方工程案例非受控实验；初始11条提示中3个误判不构成普遍误判率；计划运行不能证明真实工具状态正确。

**建议先读：**Lesson 2及Lesson 1的原始日志案例
