## 1. Systematic API Testing Through Model Checking and Executable Contracts

[原始来源](https://arxiv.org/abs/2604.08633) · [正文](https://arxiv.org/html/2604.08633v1)｜2026-04-09｜v1｜Ana Ribeiro; Margarida Mamede; Carla Ferreira

OpenAPI 能告诉测试工具有哪些接口、参数是什么类型，却通常说不清“删掉一条报名记录后，比赛里的参赛者列表也应更新”。如果只检查返回码和 JSON 格式，这种跨资源错误就可能漏掉。IcePick 改变的是测试序列的来源和执行后的判定依据：先建立 API 的有限行为模型，再从可达状态图中取出调用序列，并用可执行契约核对每一步的语义。

作者用 TLA+ 描述资源存在与否、操作前提和状态变化；这部分模型需要人工编写，不能把它理解为从文档全自动恢复真实行为。模型检查器 TLC 枚举所设有限取值范围内的可达状态，序列提取算法再寻找覆盖这些状态的路径。另一个组件 Glacier 用逻辑谓词表达操作前置条件、后置条件及始终应成立的约束，基础 CRUD 契约可从接口描述推导，领域语义可人工补充。执行时，框架把抽象动作变成真实 API 请求，并判断契约是否满足。论文中的比赛系统例子很具体：先创建参赛者和比赛、建立报名，再删除报名；即使删除调用返回正常，也要继续检查比赛是否还错误地引用该参赛者。

实验最终覆盖 Tournaments、Swagger-Petstore 和 Features-Service 三个系统，E-Commerce 因接口约定不适配推导过程被排除。作者在带故障的比赛系统中报告检出三种故障，但其中一项引用完整性问题是预实验发现的，不能全部当作独立随机注入缺陷。Features-Service 的97个错误指97次操作执行被判违约，主要涉及请求体定义缺失等问题，并非97个独立软件缺陷。模型覆盖也有明确上限：Petstore 的状态覆盖达到100%，但若两个操作连接同一对抽象状态，算法只选一个，转移覆盖仅约74%—84%。比赛模型取12个模型值时，图文件膨胀至467GB、构建耗时超过16小时；实际请求测试只运行更小配置。这些结果支持小规模、有合适契约的系统化探索，远没有证明任意 API 可穷尽验证。

**证据边界：** 有限状态模型需人工编写；完整状态覆盖不保证完整转移覆盖，状态爆炸限制可行规模。真实API测试为仿真行为验证提供方法，不是服务仿真器。

**先读：** 第IV-C、IV-D节，表IV/V。

## 2. Multi-Agent LLM-based Metamorphic Testing for REST APIs

[原始来源](https://arxiv.org/abs/2605.28321) · [正文](https://arxiv.org/html/2605.28321v1)｜2026-05-27｜v1｜Shehroz Khan; Abdullah Mughees; Gaadha Sudheerbabu; Tanwir Ahmad; Dragos Truscan

有时测试者不知道某次 API 调用应返回哪条完整记录，却知道两次相关调用的结果应有什么关系。例如修改同一只宠物的状态后，再按其标识读取，状态应变化而标识应保持。ARMeta 围绕这种“变形关系”生成测试：它不为每次请求猜一个固定答案，而是构造原始操作与后续变化，检查它们之间应满足的约束。论文重点是把这样的关系从 OpenAPI 描述落实成真正能跑的测试。

工作流先由模型提出场景，写清初始条件、施加的变化和预期关系，再由另一角色映射到具体接口并生成 Python/Behave 测试；审查与修复角色处理场景及代码问题。论文的宠物例子先创建并查询记录，然后用更新接口修改状态，再查询并检查变化。这个过程的难点不止在关系写得是否合理：若前置对象根本没创建成功，后面的关系就没有被实际检验。ARMeta 会记录请求错误、运行错误和断言失败，统计中的“失败测试”包含这些不同原因，不能一概解释为发现了状态语义错误。工作流还设操作覆盖目标、请求和时间预算，以及覆盖停滞后的停止条件。

作者在19个操作的 PetStore 和28个操作的 UserManagement 上各运行10个会话，设置每会话最多1000次请求、30分钟、两轮修复，并与直接生成调用场景的 LogiAgent 比较。PetStore 共生成211个可执行测试，其中117个失败，作者人工检查日志后认定92个是真实系统问题；UserManagement 共300个可执行测试，204个失败，116个被认定为真实问题。因此78.6%和56.9%是“失败测试中作者认定为真问题的比例”，不是对全部潜在缺陷的召回率，重复触发同一缺陷也不代表更多独立缺陷。较严格的用户管理接口会因用户名、必填项和前置准备假设错误产生更多误报。相比基线，作者找到了额外的故障触发序列；但新增序列数量与独立根因数量仍应区分，两个系统也不足以代表复杂 MCP 服务。

**证据边界：** 失败测试中的人工真问题比例不等于独立缺陷数或缺陷召回；变形关系和前置状态均须核实。真实REST服务执行，不是服务仿真。会议接收按作者稿归属。

**先读：** 图1，第III节与第IV-C/IV-D节。

## 3. Cowork-Gym: Synthesizing Interactive Work Environments at Scale

[原始来源](https://arxiv.org/abs/2610.17670) · [正文](https://arxiv.org/html/2610.17670v1)｜2026-10-13｜v1｜Anni Zou; Cheng Chen; Jiaji Deng; Weikang Zhou; Xinji Mai; Yue Wu; Jianing Lin; Lipeng Xie; Lixiong Qin; Qingyue Zhao; Que Shen; Shuchang Tao; Xuchen Pan; Yaliang Li; Yunpeng Zhai; Yushuo Chen; Zhihai Wang; Zhuo Zhang; Zhaoyang Liu; Bolin Ding; Jingren Zhou

这篇研究的对象是持续协作的工作环境：智能体修改文件、调用工具时，用户也可能追加要求或直接改动共享文件。只生成一道任务和一份静态答案，不能保证后续变化仍与工具、文件和评分标准相容。Cowork-Gym 把任务目标、初始工作区、可用接口、用户行为规则和验收器一起构造成环境，再通过实际执行与审查修复它们之间的不一致。

任务来自分类条件或已有工作资料。Builder 创建初始文件、接口和用户模拟器的私有行为规则；执行任务的智能体只能看到公开任务、工作区和许可信息，不能读取参考完成物或验收器。用户模拟器在智能体沙箱外运行，不仅发消息，也能在下一轮对话前修改共享工作区，使先前观察失效。验收器由隔离沙箱中的另一个构建角色编写，环境材料对它只读，写权限限于测试产物；它把要求对应到可观察证据，结合代码检查与语义评分，并用参考完成状态及未完成、格式错误、未改动等受控失败状态试验评分。这样的分工限制了互相改文件迎合测试的机会，但并不意味着两个角色在知识和推理上完全独立。

作者生成64,888个环境，覆盖14类场景；77,729条原始轨迹经有效性过滤保留24,732条，进一步选择17,312条用于监督微调，再在2,873个环境上做强化学习。三个规模的 Qwen 模型在六个外部智能体 benchmark 上，与各自基础模型比较，平均分分别提高约8.7、6.4、4.1个百分点；这个平均是六项评分的均值，并非所有任务统一口径的成功率，评判沿用各 benchmark 的官方指标与评估器。收益也不一致，35B-A3B 在 WildClawBench 上略降。多轮监督的比较中，27B 模型加入多轮轨迹后 ClawMark 分数高于只用单轮训练，但部分通过率没有同步上升；不能据总体增益认定每种用户干预都已被独立验证。大量原始轨迹未通过过滤，本身也说明环境数量不能直接当有效训练数据数量。

**证据边界：** 训练增益不等于对既有真实服务的行为保真；环境与轨迹过滤损耗、不同benchmark评分和个别退步必须保留。

**先读：** 第3.2节、第4节，表1/2。

## 4. AutoEnvScaling: Automating the Data Flywheel with Terminal Agents

[原始来源](https://arxiv.org/abs/2610.14163) · [正文](https://arxiv.org/html/2610.14163v1)｜2026-10-09｜v1｜Simon Yu; Baolin Peng; Bo Liu; Zhengyan Shi; Zhaoyang Wang; Hao Cheng; Qianhui Wu; Wenlin Yao; Natasha Jaques; Weiyan Shi; Jianfeng Gao

终端智能体强化学习需要大量可执行、可判分的任务环境，但让模型一次性写出任务描述、初始化文件和测试，常会留下环境无法构建或答案与测试不一致的问题。AutoEnvScaling 把环境设计本身变成终端任务：提出任务的智能体可以检查文件、运行命令、执行参考解并修复环境，而不只是输出一包代码等待外部报错。之后，求解智能体的轨迹又成为下一轮出题依据，环境池随求解能力变化。

一个环境包包含指令、初始化资源、参考解和验收程序。提出者在沙箱中构建并自检，系统再检查环境能否运行、参考解能否通过、空解是否被拒绝，并按求解表现校准任务难度。固定提出者的实验只训练求解模型；共享模型的实验则让同一模型交替承担两种角色，分别从提出和求解轨迹学习。这里的“参考解”是生成任务的一个已知完成方案，不是待复制的外部服务；“空解失败”也只是排除测试直接给分这一类明显错误。

第4.1节比较了八个提出模型的三种生成方式：仅提示生成、加入环境执行反馈，以及直接在终端中构建与修复。有效比例的分母是相应方式生成的环境，判定要求构建成功、参考解通过且空解失败。比如 GPT-5.6-sol 的比例从41.1%升至86.3%，每个有效环境的报告成本从0.90美元降至0.59美元；但 Opus 5 和 GPT-6-astra 的有效比例提高时，单个有效环境成本反而增加。因此摘要里的最高倍数和最大降本不是所有模型共同表现。论文附录F还在相同生成任务下开关参考解自检，各模型的有效产出都受益，支持“能自己运行并修复”这一机制。训练比较控制提出模型和求解更新步数，采用相同 Pi 执行框架及沙箱资源；这些控制没有匹配总计算量或墙钟时间。作者也明确承认，自检只覆盖很少的智能体行为，错误测试仍可能放过错解或拒绝正确解。

**证据边界：** 有效环境要求构建成功、参考解通过及空解失败；控制更新步数不等于匹配总计算。部分模型成本增加，自检仍可能误判。

**先读：** 第3.2节，表2，附录F。

## 5. Demystifying evals for AI agents

[原始来源](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) · [正文](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)｜2026-01-09｜official article dated 2026-01-09｜Mikaela Grace; Jeremy Hadfield; Rodrigo Olivares; Jiri De Jonghe

这篇文章要解决的是如何为多轮、会改变环境的智能体定义可靠评测。它首先区分交互记录与实际结果：智能体声称订票完成，不等于数据库中真的有预订；因此运行系统需要保存完整交互，并让评分器检查相关环境状态。文章按可机械判定的条件、需要语义判断的内容及人工校准，讨论不同评分手段如何组合，同时要求各次尝试从干净状态开始，避免先前运行留下的文件或共享资源影响结果。

对开放任务，作者建议给清晰的成功条件，避免把某条预想的工具路径误当唯一正确解；代码判定适合明确约束，模型判定则需要用人工判断校准。文章还提醒读者区分多次尝试中至少成功一次和每次都成功，两者回答的是不同可靠性问题。这是来自内部及客户实践的工程总结，没有统一样本分母和受控实验，不能写成已证明某种评分器在所有任务上更准确。

**证据边界：** 官方工程经验总结，非受控实验；任务完成、环境状态和服务行为保真是不同评价对象。

**先读：** The structure of an evaluation；From zero to one的任务歧义/隔离/评分。
