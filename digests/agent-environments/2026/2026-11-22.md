## RESTberus: Trace-Aware Benchmarking of Automated REST API Testing Tools Across Microservice Dependencies

预印本；John Toniutti、Massimiliano Baldo、Marino Miculan、Vincenzo Riccio；Udine／IMT Lucca；2026-11-03 v1，近30天补读。[原文](https://arxiv.org/html/2611.04769v1)

作者关心的不是生成更多请求，而是怎样判断测试工具究竟发现了多少种失败。一个入口服务可能把不同下游异常都包装成同样的HTTP错误；只比较返回正文，会把不同失败合并。反过来，同一个下游问题也可能从不同入口触发，按入口操作计数又会重复。孤立服务的测试方法因此不能直接回答微服务系统里的问题。

RESTberus部署目标服务及其依赖，让测试工具仍只拿OpenAPI与外部响应；评测平台另外收集跨服务调用轨迹。它把每次请求沿途发生的调用串起来，再结合返回正文归并失败。有轨迹和无轨迹的失败分开处理：前者结合路径与响应，后者按API操作分组。这是评测者增加观测能力，并没有把内部信息交给被测工具。每轮独立部署、等待服务就绪、注入随机种子，结束后收集覆盖与失败记录，以降低不同工具比较时的环境干扰。

实验在Train Ticket和PetClinic上比较六种测试工具，每个工具—服务组合重复十次，每次限制一万条HTTP请求，因此比较的是相同交互预算下的发现能力。失败归并的参照包含21,997对失败，由多模型联合标注；另有346对人工校准。混合策略在前者准确率87.1%，人工样本92.2%。这里的准确率是“这两个失败是否同类”的判断正确比例，不是发现真实缺陷的召回率；作者的标签仍存在误差，也不能把每个桶直接叫作独立根因。[方法及实验依据](https://arxiv.org/html/2611.04769v1)

阅读建议：先读III-D与表I，核清有／无轨迹分别如何归并，以及人工校准与模型标签的区别。

## SynthTools: A Framework for Scaling Synthetic Tools for Agent Development

预印本；Tommaso Castellani等；首发2025-11-11，本轮核验v2（2026-05-26）；旧文重要补读，不是版本更新推荐。[元数据](https://arxiv.org/abs/2511.09572) · [正文](https://arxiv.org/html/2511.09572)

这篇工作的目标是批量生成可供工具使用训练的环境，绕开真实API的凭据、限流和接口变动。作者先将领域细分成子领域、任务和工具，给工具配置接口、约束及描述当前任务状态的元数据；运行时由语言模型模拟响应，而不是为每个工具编写完整服务。它解决的是合成工具生态的规模与可控性，不是复制某个既定线上实现。

模拟调用先检查工具名、参数和类型等结构，再让模型判断跨字段约束以及参数是否符合当前元数据。有效调用随后生成输出：已知状态涉及的数据需要从元数据推导，其他合法输入则生成符合接口的合理数据。论文中的订票例子是根据剩余座位返回无座或票号。验证器再接收工具说明、调用及返回，判断是否正确，过滤难以稳定模拟的工具。任务构造从工具链逐步展开，每步验证可解性并更新状态，再把小任务合成完整流程；这样任务有已知解，而不是仅凭一段自然语言宣称可以完成。

实现对照证据来自ACEBench：作者对齐初始状态，在20个程序化工具上构造161次调用，模拟响应151次与参考一致，约94%。这不是全部长序列的通过率，剩余差异还包括认证检查与参数检查的先后次序。另一个人工检查集合覆盖200条响应，同样约94%；不能把不同分母的比例混为同一测试。作者还报告合成轨迹训练后工具使用成绩提升，但训练收益回答的是数据有没有用，不能反推每个环境忠实复现真实服务。[方法与对照依据](https://arxiv.org/html/2511.09572)

阅读建议：先读4.1.1及5，辨清161次实现对照的覆盖范围与逐步任务状态是怎样构造的。
