## 1. FDRRestTest: Feedback-Driven Logical Testing for REST APIs

Yutong Huo、Dongcheng Li｜中国地质大学（武汉）、Cal Poly Humboldt｜ESEM 2026，出版社发布日期 2026-10-05。[原始出版页](https://drops.dagstuhl.de/entities/document/10.4230/LIPIcs.ESEM.2026.20) · [正文](https://drops.dagstuhl.de/storage/00lipics/lipics-vol394-esem2026/LIPIcs.ESEM.2026.20/LIPIcs.ESEM.2026.20.pdf)

这篇研究的问题是，测试器能把 API 调通，却未必能发现“响应看起来正常、业务状态实际上错误”。只把服务器异常算故障，会漏掉写入没有生效、列表与详情不一致等问题；只按文档安排调用，又可能拿着已经过期的资源编号反复失败。作者改变的不是单次参数生成，而是让执行结果同时影响下一次调用的依赖、失败修复和逻辑检查。

输入是 OpenAPI 接口说明。系统先用字段名称、类型、描述及响应结构推测哪些操作产生另一些操作需要的值，形成带置信度的依赖图；执行中保存响应值，再依据值能否被后续调用成功使用，提高或降低相应依赖的可信度。失败诊断先按固定规则检查状态码、响应关键词及已有依赖，区分缺少前置资源、参数错误、约束未满足、状态过期等七类原因。证据不足就不修复；可修复时，有次数上限地替换已见值、插入前置调用、调整顺序或重新创建资源，并记住有效修正。检查器再比较响应结构、输入约束、资源生命周期和不同接口的相互一致性。例如，论文用“列表中 id 42 的名称是 A，详情却是 B”说明跨接口检查；这只是机制示例，不是一个单独的实验结果。调度器综合历史缺陷信号、尚未到达的操作、修复可能性和调用成本，决定下一条序列。[方法原文§3](https://drops.dagstuhl.de/storage/00lipics/lipics-vol394-esem2026/LIPIcs.ESEM.2026.20/LIPIcs.ESEM.2026.20.pdf)

实验在 12 个 REST 服务上给各工具 600 秒，每格重复 10 次，与 RESTler、EvoMaster、Morest、ARAT-RL、AutoRestTest 比较。表2的操作到达率为 93.3%，AutoRestTest 为 82.5%；每请求的故障信号密度为 0.9878 对 0.9294，相对提升约 6.3%。后一个分子同时计服务器错误响应和逻辑规则触发，一条响应可以触发多项，所以它既不是“98.78%请求发现独立缺陷”，也不是重建正确率。基线逻辑信号由日志事后恢复，是下界，作者明确说提升幅度属于上估计。另从六工具的 236 条去重发现中分层抽取 120 条人工判断，96 条被确认是真实缺陷；80%只适用于这批样本，不能当所有发现的真实性。系统每秒请求量更低，修复与检查也消耗时间。[证据原文表2、§4.3.6与§4.3.3](https://drops.dagstuhl.de/storage/00lipics/lipics-vol394-esem2026/LIPIcs.ESEM.2026.20/LIPIcs.ESEM.2026.20.pdf)

与工具服务仿真的关系：依赖置信度、响应值复用和有限修复记忆可支持状态探索；缺陷信号密度不能直接解释为仿真保真度。真实服务测试与生成替代服务是不同任务。

阅读建议：先读§3.4–3.7，再对照表2及§4.3.3，弄清依赖更新、修复预算和人工确认分别解决什么问题。

## 2. Automated CRUD Semantics Inference for REST APIs

Michele Pasqua、Davide Corradini、Michele Perlotto、Mariano Ceccato｜维罗纳大学、卢森堡大学、那不勒斯费德里科二世大学｜ICSE 2026，会议 2026-04-12至18；首发具体日未核。[机构记录](https://iris.univr.it/handle/11562/1193047) · [作者正文](https://michelepasqua.github.io/publications/pdfs/ICSE26.pdf)

CRUD 指创建、读取、修改、删除资源。自动测试常靠 HTTP 方法猜这些含义，例如把 GET 当读取、DELETE 当删除；但服务可能没有遵循约定，猜错后生成的调用序列和判定标准都会错。CRUDinfer 要通过黑盒交互确认操作实际做了什么，而不只根据名字或者文档分类。它仍需要 OpenAPI 说明来构造合法请求，也可以接受已有语义猜测；所谓空初始知识，并不是完全没有接口说明，而是未提供外部语义标签，工具仍以 HTTP 方法作为初始假设。

系统维护“待确认”和“已确认”的操作集合，反复为待确认操作生成专门的交互模式。确认创建时，在前后查询资源列表，并检查新资源能否读出以及内容是否与输入相符；确认修改时，创建或取得已有资源，执行修改，再读回字段，同时尽可能检查资源数量没有增加。确认删除则删同一资源两次，要求第一次有效、第二次失败，再检查列表中的资源减少。已确认操作会被用来验证其他操作，知识因此逐步扩展；无法完成验证的操作保留未确认，而不是硬填一个答案。每种模式最多生成 100 个具体测试，输入值与准备资源也会影响能否获得证据。[方法原文§3、§4.3](https://michelepasqua.github.io/publications/pdfs/ICSE26.pdf)

作者测试 13 个 API、395 个操作，每个 API 重复 10 次并恢复相同初态。真实语义由一位作者和一位外部开发专家独立检查源码，分歧交第三位专家裁决；黑盒工具的输出与这份标注比较。在这些操作中，90 个使用的 HTTP 方法与标注语义不符。表3汇总精确率为 0.95、召回率为 0.65：前者看输出的判断有多少正确，后者看应能识别的语义有多少被找到，未确认计入漏判。两者合起来说明，它偏向少误判，但仍留下不少不知道的操作。论文的 LLM 文档分类基线召回率更高，不能把本文概括成全面胜过 LLM；表3中 OWASP crAPI 的精确率也只有 0.62。登录等非 CRUD 操作没有相应模式，作者指出这是误判和漏判来源。[实验原文§4、表3–5](https://michelepasqua.github.io/publications/pdfs/ICSE26.pdf)

与服务仿真的关系：应区分文档假设和交互确认的语义，保留未确认项。论文要求第二次删除失败，但有些真实服务允许重复删除；仿真验证需以实际参考行为为准，不能将规范检查替代行为对照。

阅读建议：先读§3.2的创建、修改和删除模式，再看表3与§4对失败原因的解释，关注确认条件什么时候会把真实行为排除在外。

## 3. Checking Security Properties of Cloud Service REST APIs

Vaggelis Atlidakis、Patrice Godefroid、Marina Polishchuk｜Columbia University、Microsoft Research｜技术报告 2019-02，微软页注明修订版 ICST 2020；会议版题名为单数Service。[微软原始记录](https://www.microsoft.com/en-us/research/publication/checking-security-properties-of-cloud-services-rest-apis/) · [会议正文](https://patricegodefroid.github.io/public_psfiles/icst2020.pdf)

返回码相同不代表服务状态相同。这篇论文从真实云服务故障出发，把原来主要寻找服务器异常的 RESTler 扩展为会主动追加请求的属性检查器。作者提出四条期望规则：删除的资源不能继续访问；创建失败不能留下可见副作用；子资源不能借另一个父资源访问；某用户的资源不能通过另一个用户的身份访问。检查器的作用不只是观察已有流量，而是在主测试器刚刚创建、删除或失败的时刻，生成能暴露相应问题的后续调用。

系统输入仍是 Swagger/OpenAPI 说明和参数字典，主测试器生成有资源依赖的序列，保存执行得到的资源编号。检查器在合适的触发点接管这些编号：删除后再尝试消费已删除资源；创建失败后继续访问相关编号；层级检查则替换父资源编号，保留子资源编号；身份检查改用另一用户的凭据。各检查器需要维护和恢复自己的测试上下文，避免附加调用污染其他检查。作者还提供优化模式，省略预计重复的检查，以免测试成本都花在同一状态附近。[方法原文§III](https://patricegodefroid.github.io/public_psfiles/icst2020.pdf)

论文中的真实案例是：用错误请求体创建名为 X 的资源，服务返回 500；随后查询列表为空，看起来创建完全失败；再用正确请求体、相同名称但另一地区创建，却返回 409 冲突。第三步才暴露后端仍记住第一次失败尝试。只检查第一步响应或第二步列表都会错过这类残留。作者在两个 Azure 管理服务和一个 Office365 消息服务上评估，接口分别有 13、19、18 种请求，同一服务各实验使用相同语法和参数字典，每次一小时。表II显示，优化模式保留穷举检查模式找到的缺陷类别，并降低检查调用占比，例如 Office365 从 11.4%降到 4.1%。这是三个服务内的成本结果，不是对任意服务都不漏检的保证。全部实验报告给开发者的独立缺陷共 7 个，不能将表中每个请求或每个告警桶相加当成新缺陷数。[实验表II与真实案例§V](https://patricegodefroid.github.io/public_psfiles/icst2020.pdf)

与状态保真的关系：失败请求后的列表为空仍可能留下名称占用。后续序列能暴露隐藏副作用，可用于比较真实服务与模拟服务的状态变化；安全规则只适用于具有对应身份或资源机制的系统。

阅读建议：先读§III-B的检查器如何插入调用，再读§V的resource-leak案例，看清为何“失败后列表为空”仍不是状态无变化的充分证据。

## 4. RESTler: Stateful REST API Fuzzing

Vaggelis Atlidakis、Patrice Godefroid、Marina Polishchuk｜Columbia University、Microsoft Research｜ICSE 2019；同系早期报告与2018预印本归并，不另计。[微软记录](https://www.microsoft.com/en-us/research/publication/restler-stateful-rest-api-fuzzing/) · [正文](https://www.microsoft.com/en-us/research/wp-content/uploads/2021/03/RESTler.pdf)

RESTler 面对的障碍是，服务许多功能只有先建立正确资源才能访问。随机生成一个项目编号再调用提交接口，大多只会得到不存在；即使所有接口各调用过一次，也不等于走到依赖项目、提交和分支的深层状态。它用接口说明推测“哪个请求产生哪个请求需要的资源”，再用执行反馈控制序列扩展，把测试从随机单次请求变成有依赖的多步探索。

具体输入是 Swagger 说明与有限参数字典。编译器生成请求模板，识别响应中的资源编号，并把产生值的请求与消费值的请求连接起来。执行序列时，前面响应中提取到的编号进入后续模板，而不是重新随机猜测。若一个请求在当前前缀后被服务拒绝，工具不再把这条无效序列继续向深处扩展；成功的前缀则可追加满足依赖的请求。广度优先搜索尽量列举同一长度的组合，BFS-Fast 减少保留的序列，随机游走倾向走更深；三种策略在搜索范围和深度之间取舍，而不是一种覆盖全部可能性。[方法原文§III–IV](https://www.microsoft.com/en-us/research/wp-content/uploads/2021/03/RESTler.pdf)

作者先在可解释的小型博客服务上做消融，固定探索到长度3，分别去掉依赖推断或动态反馈。去掉依赖时，无法把先前读出的校验值送入后续修改操作，漏掉作者植入的异常；保留依赖再加入反馈，则压掉大量无效组合，保留能触发异常的序列。这里的已知植入故障说明两个机制怎样互补，不是发现自然缺陷的总体成功率。GitLab 的后续实验在不同接口组及相同时间预算下比较深度、代码覆盖与错误桶；深度更大并不总有更高代码覆盖。论文摘要汇总 GitLab 28 个已确认并修复的缺陷，表III那组搜索策略实验为22个，二者是不同统计范围，不混用。[实验原文§V–VI](https://www.microsoft.com/en-us/research/wp-content/uploads/2021/03/RESTler.pdf)

与环境探索的关系：有依赖的多步调用可帮助收集状态证据。RESTler在真实服务上查找故障，并不生成模拟器；失败前缀剪枝可能遗漏失败调用的副作用，不能直接当作完整行为覆盖。

阅读建议：先读图3的序列生成算法，再看图4的两种机制消融，检查剪掉无效前缀节约了什么、同时可能漏掉什么。

## 5. RESTCov: A Tool for Structural Coverage Analysis of REST APIs

Tolgahan Bardakci、Serge Demeyer｜University of Antwerp／Flanders Make｜arXiv v1，2026-08-28，预印本。[原始记录](https://arxiv.org/abs/2608.28114) · [正文](https://arxiv.org/html/2608.28114v1)

这篇工具论文关注一个比找缺陷更基础的问题：没有服务源码时，怎样知道接口说明中的哪些部分已经被测试流量触及。RESTCov 不生成请求，也不学习服务实现；它把 OpenAPI 定义与配对的 HTTP 请求、响应日志放在一起，按文档结构计算覆盖率，给测试器提供一份可复查的覆盖报告。

处理首先是把日志中的路径对应到接口模板。例如带资源编号的路径需要匹配文档里的参数占位符，再结合 HTTP 方法识别操作。工具去除服务器地址和基础路径前缀，但保留路径大小写、尾部斜杠和编码差异；未匹配请求单列，避免悄悄当成某个合法接口。随后分别统计路径、操作、参数、请求及响应媒体类型、响应状态码及状态类别。每个分母来自说明中定义的元素，分子来自日志实际见到的元素，读者因而能区分“端点调用过”和“文档列出的失败响应也试过”。[处理与指标原文](https://arxiv.org/html/2608.28114v1)

正文展示的是 Petstore 演示，而非多服务的算法优越性实验：14个路径、20个操作和25个参数都达到100%，但36个文档响应状态码只观察到14个，覆盖率38.9%。这些数说明，一张“接口都测试了”的表仍可能漏掉许多返回分支；它们没有证明测试到了哪些状态转移，更没有证明每个响应正确。示例中带异常编码的上传路径未匹配，也说明日志归一化规则会改变覆盖分母和解释。作者提到工具在其他生产 API 工作中的使用，但本文并未展开足以支持广泛效果结论的多服务比较。[演示原文](https://arxiv.org/html/2608.28114v1)

与仿真验证的关系：结构覆盖适合审计已观察的接口、参数和响应分支，但不等于状态转移覆盖或行为正确性。HTTP指标迁移到其他工具接口时需重新定义分母。

阅读建议：先看Petstore覆盖表及未匹配请求示例，确认每个100%的分母是什么，以及它没有覆盖哪些行为。
