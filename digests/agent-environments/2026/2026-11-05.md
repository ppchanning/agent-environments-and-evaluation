## 1. ToolSpace: Scaling Tool-Centric Environment Synthesis for Long-Horizon Agents

中国人民大学、复旦大学、上海交通大学；Guanting Dong、Zhichao Sun、Xinyu Yang等。预印本，新作；首发及核验版本v1：2026-11-03。[原始摘要](https://arxiv.org/abs/2611.05036)｜[正文](https://arxiv.org/html/2611.05036v1)

作者要解决长链工具训练数据难以扩大的问题：先编数据库、再编工具和任务，容易得到与真实接口脱节的工作流。他们改从调用记录出发，按相邻调用之间的数据传递、同一对象的状态读写及失败后重试建立图，连边由规则识别、按出现频率加权；不是让模型凭工具名称猜关联。语料包含真实服务执行，也包含筛过接口格式的合成工具轨迹，不能统称全是真实执行。

系统只为含增删改的环境合成数据库；查询返回可以锚定初始快照，无状态工具则对匹配调用使用缓存返回。沿图采样时，下一步参数必须能从现有状态或先前返回中取得；执行失败或关系不一致便恢复上一步快照、换路。成功链再被改写成不泄露工具顺序的自然语言任务，并检查最终状态、中间轨迹及返回字段；只有从初态重放通过才收录。因此，它验证的是所造任务在这个执行体系内可走通。

作者在七个工具使用benchmark上报告，Qwen3.6-35B-A3B经监督训练后的平均分由23.0升至41.0；这是七项分数的平均，不是所有调用的正确率。各benchmark沿用其评分协议，论文同时使用外部已发布分数与本地复现，比较并非全由同一实验室重新执行。这个结果支持训练数据的效用，却没有直接度量原服务与合成服务逐调用相符的比例。（见正文§4、§6及表1。）

来源：https://arxiv.org/abs/2611.05036 · 建议先读：§4.1.3、算法1及§3末段。

## 2. Behavioral Skill Reconstruction: Reconstructing Hidden Functionality from LLM Agent Skills

南加州大学；Peichun Hua、Haoxuan Xu、Mengyuan Li。旧文补读，预印本；首发2026-08-04，核验v2：2026-09-19，本轮不声称版本新更新。[原始摘要](https://arxiv.org/abs/2608.04192)｜[正文](https://arxiv.org/html/2608.04192v2)

这篇研究把“看不到实现”与“无法复制功能”分开。服务可以藏住技能文件，调用者仍可能从正常请求与回答中重建其规则。SkillClone只看公开介绍、任务接口以及可见回答或产物，先猜输入输出及潜在因素，再设计能区分假设的探测，解析答案，生成独立可执行程序，最后依据程序与目标回答的分歧修补。它不要求目标泄露源文件。

论文中的说明例子是文档优先级：固定字数换关键词，再固定关键词测试500与501词，随后组合条件，区分“长度足够即可”还是“长度与审核主题同时满足”。这是作者用于讲方法的例子，并非整个实验的成功率。核心过程是让每次查询排除一种解释，而不是随机攒一批问答后一次生成代码。候选程序的选择依据是与服务在验证输入上的一致程度。

实验覆盖30项技能，最后由调用者不可见的确定性参考实现检查留出输入。主设置有52次建模探测，另加30次验证查询，共82次；SkillsBench设置则为24加30，共54次。作者还把失败因素拆开诊断：r2r目标回答算错隐藏常数相关的量时，克隆在参考测试上的一致率为0%；改给正确参考标签，同一重建过程达到100%。这支持“观察信号可能是瓶颈”的解释，不能把它概括成换模型便能解决全部重建问题。（见§3、§4.2—4.3、§5.1。）

来源：https://arxiv.org/abs/2608.04192 · 建议先读：§4.3、§5.1及§3例子。

## 3. Willful Disobedience: Automatically Detecting Failures in Agentic Traces

Microsoft Research、华盛顿大学；Reshabh K Sharma、Shraddha Barke、Benjamin Zorn。旧文补读；首发2026-03-25，核验v2：2026-05-08；正文标注ACM CAIS 2026及DOI。[原始摘要](https://arxiv.org/abs/2603.23806)｜[正文](https://arxiv.org/html/2603.23806v2)｜[正式标识](https://doi.org/10.1145/3786335.3813153)

AgentPex关心的是：只看最终结果，会不会漏掉代理违反流程的行为？即使最终数据库改对了，代理也可能跳过确认或用了不被允许的调用顺序。作者将提示词、任务、工具定义和执行记录整理为统一输入，提取输出要求、步骤约束、禁止相邻调用及参数规则，再用模型检查记录是否遵守；还依据任务预测计划和最终状态。这让“做成什么”与“怎样做成”能够分别受到检查。

检查器会返回分数及解释，不只是一个总判定。汇总时先求加权平均，再由关键检查项中的最低分封顶，防止一般项目的高分掩盖关键失败。这里的规则并不全是同一种依据：系统明示的限制与模型推测的合理计划，可信度不同；后者若排除了合法替代路径，低分未必意味着真实违规。这也是把这类工具用于科研评测时必须回看具体证据的原因。

作者从电信、零售、航空客服任务选取三种代理模型的450条记录，并在过滤不完整评估响应后分析424条，规则抽取与评分由GPT-5 mini完成。样本刻意平衡了任务、复杂度和约35%的成功率，因此不是生产失败率调查。相对于τ²-bench的人工参考结果，单独的输出规范检查器判别任务失败的ROC-AUC为0.680；它表示对失败与成功记录的排序区分力，不能解释成68%的整体评测准确率，也不是七项汇总评分的结果。（见§3—4.2。）

建议先读§4.2，再读§2的动机例子，看清它何时借助结果标签验证自己、何时只能根据记录提出违规判断。


来源：https://arxiv.org/abs/2603.23806 · 建议先读：§4.2及§2。

## 4. Introducing AgentEnv: An Open-Source Framework for Building RL Environments

Scale Labs；Edgar Arakelyan、Tejas Polakam、Yzabelle Go。官方实质技术文章，2026-10-05；距今31天，明确作旧文补读。[原文](https://labs.scale.com/blog/introducing-agentenv)

这篇文章解决环境工程的组织问题：若每个任务都另建一套世界，工具、数据和评分会反复耦合，修改一个基础环境也难以复用。AgentEnv先定义可复用世界，再让多个任务在其中运行。它把环境、填充环境的数据产物、控制时钟与角色等行为规则作为可组合且有版本的部分；环境卡声明可用工具和接入方式，支持MCP、REST或命令行调用。

任务本身是有依赖关系的步骤图：先准备世界、装载数据和设置时钟，再让代理工作、收集产物，最后按任务选择严格检查或评分规则。原文用客服退款和三维建模说明：相同基础设施可以服务不同目标，而有的任务只是交互试验，并没有自动评分器。这一点避免把“环境可运行”误当成“已经形成可信benchmark”。文章展示的是框架结构和示例，没有给出与真实服务逐项对照的误差测量或受控性能比较。（见原文Building Blocks及任务构建部分。）

来源：https://labs.scale.com/blog/introducing-agentenv · 建议先读：Building Blocks and Interoperability及任务构建。

## 5. Evaluating AI agents: moving past the vibe check

Google Developers Blog；Hugo Selbie、Dani Zamora、Jesse Carah、John DeMartino。官方实质技术文章，2026-10-15；近30天补读。[原文](https://developers.googleblog.com/evaluating-ai-agents-moving-past-the-vibe-check/)

文章讨论代理迭代时常见的错觉：答案看起来仍然合理，内部却多了循环、漏了工具步骤，或者评测集自己发生了变化。作者从一条具体用户旅程拆出验收条件，而非先找一个泛化总分。文中的金融核对例子要求识别争议交易、查内部账本、把内部交易编号换回外部称呼后起草回复；这些条件分别对应可检查的行为，最终文本流畅并不能替代其中任何一项。

随后，作者建议先用带人物设定和行为约束的模拟用户产生交互记录，待上线后逐步用真实流量补充。检查覆盖单元测试、确定性指标、模型判断与集成测试，并把能明确回答的问题写成通过或失败，而非含义漂移的五级评分。它特别强调调功能期间冻结基准集、一次改变一个因素，同时记录延迟、token、费用及工具调用数。这里是工程方法说明与演示，没有报告一组受控实验来量化该流程优于其他方案多少。（见原文Getting started及Four common traps。）

来源：https://developers.googleblog.com/evaluating-ai-agents-moving-past-the-vibe-check/ · 建议先读：Four common traps前3项及用户旅程例子。
