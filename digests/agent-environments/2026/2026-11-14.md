## 1. Testing Conversation Preservation Across LLM APIs: A Rule-Based Oracle for Detecting Silent Information Loss

[原始来源](https://arxiv.org/abs/2611.15543) · 版本 v1 · 

把一种模型API转换成另一种，往往被当作字段改名。但作者关注的是：转换后的请求即使能被目标接口接受，是否还保留原来的信息？例如，工具执行失败的结果仍有文字内容，却丢掉表示失败的`is_error`；模型看到的就不再是同一种反馈。另一个论文案例是对话中途出现的系统指令：若被删除或降成普通用户文本，其约束后续工具使用的权限也会改变。这些差异不是检查JSON类型就能发现的。

作者的工具isloss先把转换前后的消息都整理成共同表示ConvIR。它记录谁在说话、指令权限、内容与顺序、工具调用及结果的对应关系，也记录生成控制参数；随后用27条显式规则比较。正常的工具ID重命名、保持信息的消息合并不应误报。目标API确实不支持某项能力时，也要与转换器本来能够保留却丢弃的信息区分。检查器本身不依赖调用模型来猜两段话是否等价，代价主要在预先建立规则、处理各API的表示差异。

在独立保留的人工植入测试中，检查器发现125个故障中的95个；对100个允许的变换误报2个。作者又检查五个转换器代码库的六种配置：685次完成的转换中，127次出现格式有效、却丢失目标本可保留的角色、提示或工具信息。这是论文构造语料和配置下的计数，不能直接当成真实业务流量的故障率。它支持“接受请求不足以证明保留信息”，没有证明规则已经覆盖全部行为差异。[证据与规则原文](https://arxiv.org/html/2611.15543v1)

建议先读§3.1–3.2及图3，再看§4.2，弄清哪些变换被允许、哪些信息损失被计为错误。


## 2. MASTOR: A Multi-Agent Approach to Semantic Test Oracle Generation for RESTful APIs

[原始来源](https://arxiv.org/abs/2606.10465) · 版本 v1 · 

很多API测试能发现崩溃或返回类型错误，却不知道业务结果有没有错。论文中的过滤字段案例很直观：请求只要指定字段，响应返回的却是其余字段，类型仍然完全合法。另一个例子是捐款接口返回受理状态，但真正需要核对的是向支付系统发送的金额、币种等参数；仅检查眼前响应，可能碰不到关键副作用。这里的oracle指测试的判错依据，不是另一个生成答案的模型。

MASTOR从OpenAPI说明定位源码中的端点，再沿Java导入依赖收集相关上下文，供模型理解实现。它把断言生成分为两条路径：一条围绕单次操作的状态码和字段语义，另一条寻找跨操作的关联，让前一步产生的事实在后续操作中接受检查。生成结果经过质疑与定向修改，并由规则处理结构问题，最终形成可转成JUnit或Postman检查的结构化断言。其关键优势不仅是分工，还在于读到了通常不会完整写进接口文档的实现条件。[方法原文](https://arxiv.org/html/2606.10465v1)

作者在13个开源Java REST API、296个操作上评估，报告平均变异得分75.4%：向程序植入小改动后，断言能否让原本通过的测试失败。分母按论文定义包含杀死及存活的变异体，不包括没有覆盖到的部分，也没有消除所有等价变异，不能理解成发现了75.4%的真实漏洞。对齐的50个操作只比较状态码与字段断言时，MASTOR、直接提示和SATORI分别为69.9%、39.8%、20.5%。不过MASTOR拥有源码，而文档方法的信息更少，因此差距不能全部归因于多智能体设计。[实验原文](https://arxiv.org/html/2606.10465v1)

建议先读§3的两个案例和§5.2.2的指标定义，再看比较结果，明确源码权限与变异分母。


## 3. SATORI: Static Test Oracle Generation for REST APIs

[原始来源](https://arxiv.org/abs/2508.16318) · 版本 v2 · 元数据 v2，正文仅定向核验 v1。

SATORI问的是：尚未大量调用服务，仅靠OpenAPI说明，能不能生成比“类型正确”更具体的断言？它与从历史执行结果归纳规律的方法形成对照。后者需要足够丰富的输入才有机会看出取值范围，文档却可能直接写明范围。论文的Yelp例子包括评分应在1到5、国家代码有规定长度、价格字段来自有限取值；错误响应仍可能完全符合字符串或数字类型。

方法先为响应字段提取名字、描述、示例和模式信息，并加入整个API及当前操作的上下文。模型按预设的17类断言生成结构化结果，随后处理这些结果，并通过扩展的PostmanAssertify转换为Postman可执行的JavaScript断言。这里“静态”指生成时不需要先运行API，并非执行测试也不需要服务。规则可以进入人工检查流程；自然语言说明若含糊或过期，模型生成得再流畅，也不能自动变成实际服务的正确行为。[方法原文](https://arxiv.org/html/2508.16318v1)

作者使用OKAMI中12个工业API的17个操作，人工标注超过1800个响应字段的万余条断言作为参照。在可比较断言类型上，SATORI的F1为74.3%，动态方法AGORA为69.3%；F1综合了生成内容中有多少被标注认可，以及应有内容找回多少，并不是API任务成功率。两种方法合并可覆盖约90%的标注断言，说明文档信息与运行轨迹可能互补；这也不代表捕获了90%的真实故障。本文另有故障检测实验，不能把那里的检出数量与上述标注覆盖率混用。[评估原文](https://arxiv.org/html/2508.16318v1)

建议先读§III及图1，再读§IV-A的人工参照定义，核对“断言正确”到底相对于什么。


## 4. CRAB-Bench: Evaluating LLM Agents under Complex Task Dependencies and Human-aligned User Simulation

[原始来源](https://arxiv.org/abs/2606.01815) · 版本 v1 · 

在旅行任务中，机票、酒店和景点各自看起来合适，并不代表整段行程成立。论文关注现有代理评测中容易被简化的依赖关系，以及过于配合的模拟用户。它用任务图表示各项选择及其联系，把时间、预算等要求变成可求解的约束。例如酒店安排必须与航班时间相容，不能只分别判断一次订票和一次订房是否成功。

构造任务时，约束求解器先给出可行方案，再把候选数据放入环境，并添加单看合理、组合起来却不满足约束的干扰项。这让代理需要查询和协调多次选择，而非捡到明显答案。评测检查最终数据库状态是否满足任务约束，允许存在多个有效方案。另一部分RUSE模拟用户，从沟通方式、信息披露、澄清行为和面对错误的反应等维度设置差异，生成简短、中性或不耐烦等行为。用户不再总会一次说全信息、自动帮助代理纠错。[构造与交互原文](https://arxiv.org/html/2606.01815v1)

作者构造200个旅行任务，四档难度各50个，提供19种代理工具和7种用户工具。四个前沿模型在通用用户条件下，最好结果是DeepSeek-V3.2的单次成功率0.61；这里成功由任务条件与最终状态检查决定，分母是该基准任务，并非真实用户订单。换用RUSE后表现下降，支持用户行为会改变测量结果的判断。不过行为设定有文献依据，不等于已经通过真实用户实验验证全部模拟行为；对话表现与数据库中的完成状态也不是同一指标。[实验原文](https://arxiv.org/html/2606.01815v1)

建议先读§3.2–3.4及图1，再看表2，分清任务约束、用户行为与环境转移各由谁决定。


## 5. From Business Requirements to Test Assertions: Evaluating LLM-Generated Oracles on Real Bugs

[原始来源](https://arxiv.org/abs/2607.10277) · 版本 v1 · 

这篇小规模研究最有价值的地方，是把“按业务需求应当怎样”与“程序实际怎样”分开作为参照。作者从Defects4J的Lang项目挑选10个真实缺陷，依据缺陷及修复差异人工写出业务需求，再让模型生成Java测试断言。模型获得需求和方法脚手架，不直接读取实现源码或成对输入输出，因此研究的是需求能否支持判错，而非模型能否复制既有程序。

评估时有两套依据：一套是作者按照需求建立的人工断言，另一套是被测系统的实际行为。生成的断言经过编译和运行，再与两套依据比较。这种安排使同一份生成结果可能在“符合需求”上得分较高，在“符合实现”上较低。数值类型提升之类的细节较难从概括需求恢复；较明确的结构化规则则更容易写成检查。需求不是自动从真实业务现场获得，而是由已经知道修复差异的研究者整理，这会影响它能代表什么场景。[设计原文](https://arxiv.org/html/2607.10277v1)

作者比较五个模型。以DeepSeek为例，对10个缺陷的宏平均F1，相对于系统行为为0.7476，相对于需求参照为0.8179；宏平均意味着每个缺陷先算指标再平均，不是所有断言混在一起的正确率。部分模型存在编译失败并被排除的样本，所以表中的可评分结果也不是从生成到运行的端到端可靠性。需求和人工参照由相同研究过程产生，且只覆盖一个Java项目的10个缺陷，不能据此推断所有需求都能替代实现，也不能把弱相关分析当成需求复杂度没有影响。[结果与限制原文](https://arxiv.org/html/2607.10277v1)

建议先读§4.1–4.3、表3和§6.3，核对两套参照的来源及编译失败样本如何处理。
