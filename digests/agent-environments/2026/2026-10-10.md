## 1. ProgramDistill: From Interactive Web Apps to Verifiable Reference-Guided SWE Tasks

近30天补读；arXiv预印本v1，2026-09-16；Jeonghye Kim等，KAIST、Microsoft Research Montréal、Microsoft AI。[论文](https://arxiv.org/abs/2609.18805)｜[核验正文](https://arxiv.org/html/2609.18805v1)｜[作者团队介绍，9月14日](https://microsoft.github.io/debug-gym/blog/2026/09/programdistill/)。博客与论文归并一项。

多数代码评测先给问题描述，再让 agent 修改仓库。ProgramDistill 改变的是“正确行为从哪里来”：参考应用可以操作，但源代码隐藏，agent 必须通过交互理解它，再修改自己手中的应用，使相同操作产生相应结果。作者同时研究缺损应用修复与从最小可运行框架重建整套应用；前者已有大量实现，后者才更接近从零重建，阅读时不能把两种难度混在一起。

任务由三步制作。首先，采集 agent 在参考应用中发现功能、记录动作及可检查结果，再重放验证；每个行为还记录成立所需的前置状态。随后另一过程删除对应实现，检查目标确实失效、前置行为仍能工作，并保留能恢复功能的补丁。最后，评测 agent 只能操作参考应用、编辑当前应用，提交后用固定动作和结果检查恢复程度。作者将时间、随机性等运行因素控制为可复现设置，浏览器工具提供结构化页面观察；它不是直接以截图相似度代替行为。论文中“创建看板和卡片，再打开编辑器”的例子说明了依赖关系：前半段成功不能抵消后半段失败，完整工作流得分要求全部目标通过。

作者从26个应用得到1,975个验证行为、4,063个任务，但完整重建实验使用其中12个应用，检查590个原子行为与413个累积工作流。三种模型在同类任务上比较，最强模型的原子恢复率均值为58.98%，累积工作流均值为49.15%；后者是按应用汇总的均值，不是“通过约一半全部413条”的直接计数。证据说明整套交互功能仍难恢复，也说明只看单点成功会高估能力；它没有测遍应用全部行为。原文还给出未观察到功能、观察后遗漏以及状态或路由恢复错误等失败分类，这些是作者的归因，不等于分别干预后证明了因果关系。

阅读建议：先读§2.4与§3.3及表1，看清完整重建允许观察什么，以及一个功能通过和整条工作流通过如何分别计分。

## 2. Differential Regression Testing for REST APIs

旧文补读；ISSTA 2020，会议日期2020-07-18—22；Patrice Godefroid、Daniel Lehmann、Marina Polishchuk，Microsoft Research与University of Stuttgart。[微软原始页面](https://www.microsoft.com/en-us/research/publication/differential-regression-testing-for-rest-apis/)｜[作者原文PDF](https://patricegodefroid.github.io/public_psfiles/issta2020.pdf)。2019年技术报告与2020年会议论文为同一工作，不计新作。

云 API 的升级有两个变化源：服务实现变了，描述允许请求和返回结构的规格也可能变了。因此，今天的客户端失败，未必是服务做错了，也可能是新规格不再允许旧调用。作者不是把新旧返回文本直接做差，而是把客户端所依据的规格版本与服务版本分开，固定其中一边再比较另一边。这样才能判断差异来自哪里；同时更换两边，反而可能让原有问题被一起掩盖。

具体执行时，RESTler 从 OpenAPI 规格生成有依赖的请求序列，保存请求与响应日志。例如，原文用先创建博客文章、再为文章创建评论说明为什么请求不能任意独立发送。比较日志之前，要把日期、请求跟踪号、随机资源名称等正常变化抽象成常量，并按 JSON 结构递归比较。这里的抽象是按正则和服务规则指定的，不是模型自动知道所有无关字段。作者又提供更粗的比较方式：按请求类型分组，只比较响应状态，忽略完整历史与响应内容。它能减少规格调整造成的顺序噪声，却会丢掉正文中的错误，因此原文把两种方式用于不同变化方向。

作者检查 Azure 网络 API 的17个历史版本及DNS服务版本，人工检查日志差异后确认14处回归，其中5处属于规格、9处属于服务。最有启发的证据是：固定规格比较服务时，粗比较的98%差异文件为空，但细比较发现了新增且未及时写入规格的响应字段。由此可见，“两边都返回成功”不足以判断兼容。较省成本的相邻升级比较，在这个样本上仍找到全部14处；该结论依赖这里的版本、生成器和兼容关系，不是对任何服务的保证。作者还记录了92,381次请求和约一周人工检查，说明找差异与确认差异是两项成本。

阅读建议：先读§3.3—3.4及§4.5.1，看清两种日志比较保留了什么，以及简化比较漏掉了哪些证据。

## 3. You Can REST Now: Automated REST API Documentation and Testing via LLM-Assisted Request Mutations

RESTSpecIT 解决的是接口规格缺失：不知道服务有哪些路径和参数，就难以使用依赖 OpenAPI 的测试工具。它让语言模型提出可能的请求，再到真实 API 检查，而不是把模型回忆出的文档直接当成事实。输入通常是服务名称及模型调用配置；本地服务地址和访问密钥可另提供。输出是发现的路径、参数与机器可读规格，尚不是服务的行为实现。

过程先尝试获得基础地址与若干有效调用，再从成功请求中选种子，把路径或参数的一部分遮住，要求模型提出替代值，将候选逐一发往服务。通过检查的新调用又成为种子，继续扩大探索。例如原文将图书路径遮住后尝试人物、家族等路径，实际无效的候选被丢弃。成功状态码并不直接算有效：还检查短错误消息、HTML响应等情况。v2也描述了写入方法的处理，POST要生成JSON内容，DELETE可针对刚创建的资源；不过这种支持不能自动说明已推断完整状态语义。探索连续两轮没有新路径或参数时停止。

v2的主要实验为10个 API，比较DeepSeek V3、GPT-4.1-mini及GPT-3.5-turbo，各独立运行5次，以参考文档计算发现比例。DeepSeek的平均路径覆盖为88.62%，参数覆盖为89.25%；这些数字不是副本正确率，也不是v1摘要中的85.05%和81.05%。更有信息量的是作者另造三个模型不知道的本地API，每个10条路径、10个参数：平均发现比例降到58.67%与71.00%。这支持方法确实能探索陌生接口，同时提醒公开服务上的高表现可能受已有知识帮助。作者也承认服务可能忽略无效参数，导致“请求成功”被误解为“参数有效”；实验在全部文档项已找到时会提前停止，其成本条件也不能照搬到未知规格任务。

阅读建议：先读§3.3—3.4、§4.2及§5.1和表5，看清候选如何被验证，以及陌生API上的结果为何低于公开服务。

## 4. RESTOR: Automated Test Oracle Generation for RESTful APIs via Reinforcement Learning

旧文补读；arXiv v1，2026-07-27；Xun Zhou等，复旦大学、ByteDance；正文列出PACMSE/ISSTA论文信息及DOI。[原始论文](https://arxiv.org/abs/2607.23963)｜[核验正文](https://arxiv.org/html/2607.23963v1)｜[正式DOI](https://doi.org/10.1145/3832185)。本次实验解释依据arXiv正文，未另核正式出版日期。

测试不仅要发请求，还要知道返回是否符合业务要求，这种判定规则叫测试预言。文档不足时，模型容易只检查字段存在，或者把观察到的时间戳写死，前者漏错，后者产生不稳定测试。RESTOR希望从一个请求—响应样本生成可执行断言，但“单样本”指部署时的输入，并不意味着训练不需要业务资料和人工判断。

作者先收集工业流量，由人标出重要字段与语义约束，再生成合法变体与违反约束的变体来训练模型。每次模型生成断言，先检查代码能否执行且接受原始响应；不通过就受罚。接下来奖励它覆盖重要字段、避开动态噪声，最后检查断言能否接受合法变体、拒绝错误变体。这样，输出不必机械复制原值。论文中的订阅接口例子涉及订阅类型的允许取值、开始与结束时间的大小关系及布尔字段，体现了“允许合理变化，但拒绝破坏规则”的区别。

数据覆盖246个服务、15条业务线和超过2,300条流量样本；主实验用229个留出样本，与同一基础模型及DeepSeek的提示方法比较，各模型采用相同系统提示。重要字段选择的F1为85.42%，其意义是兼顾应检查字段的覆盖与选择准确度，不能读成整体测试正确率。作者还由QA人员建立多数一致的语义判断，报告断言完整性改善；工业部署的采用率从74.1%升至超过96%，衡量的是生成结果进入人工审核后的采用情况，不是无人工审核的正确率。正文称排除了测试端点的训练污染，但全部数据仍来自同一公司，外部服务上的效果需要另证；关键字段标注和约束制作也有显著人工成本。

阅读建议：先读§3.2.2与§5.1、§7，看清奖励所依赖的人工规则，以及单次流量输入背后的训练与审核条件。

## 5. WFC/WFD: Web Fuzzing Commons, Dataset and Guidelines to Support Experimentation in REST API Fuzzing

旧文补读；arXiv v1，2025-09-01；Omur Sahin、Man Zhang、Andrea Arcuri。[原始论文](https://arxiv.org/abs/2509.01612)｜[核验正文](https://arxiv.org/html/2509.01612v1)。

这篇关心一个容易被算法排名掩盖的问题：不同 API 测试工具拿到的环境条件未必一样。有些工具能完成认证，有些根本进不了受保护接口；同一故障又可能被不同工具以不同粒度报告。直接比较覆盖率或“发现错误数”，就可能把环境接通能力、报告格式和搜索能力混成一个结论。作者因此提出认证配置与故障报告的共享格式WFC，并整理带有运行支架的API集合WFD。

输入不只是 OpenAPI 文件，还包括如何取得或刷新凭据、如何启动服务等运行信息。WFC把这些操作需要的信息显式表达，工具再按支持情况使用；故障报告则使用共同类别，使状态码、响应格式等不同问题可以分开统计。WFD包含36个开源API及相应实验支架，目的是让研究者更容易在同一批对象上比较工具。这里统一的是评测条件和数据格式，不是替工具生成服务副本，也不是自动消除所有环境差异。

作者比较六种模糊测试工具，每个API按一小时预算、十次重复组织实验；名义组合为2,160组。原文主动披露了条件差异：EmRest因依赖问题换到Mac运行，其中两个API又受M4架构的容器镜像限制；统一认证格式当时只有EvoMaster支持，因而可能给予它优势。所以作者强调这项研究不是宣判哪个工具最好。另一个实际问题是，测试运行时产生的覆盖，与保存下来可独立重跑的测试覆盖不同：调用日志或curl命令也不等同于带断言的可执行测试。论文讨论了删除资源导致后续测试失败的情况，说明测试本身也需要建立自己的前置状态。

阅读建议：先读§4.1、§6实验设置和§6.2，看清认证及平台差异如何影响比较，以及保存的测试是否真正可重跑。
