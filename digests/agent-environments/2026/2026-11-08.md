## 1. LegoEnv: Self-Evolving Agentic Environments via Modular Recombination

[原始来源](https://arxiv.org/abs/2611.01834)｜2026-11-01；v1。

作者针对的是自动造环境时的重复劳动：每次重新生成一个完整服务，会重复制造相同缺陷，修好一处又不能惠及其他环境。LegoEnv把环境拆成可复用的服务实现、数据、用户意图和业务规则。组合之前先检查某个意图需要的操作是否有工具支持、规则依赖的对象是否有服务承载，再让构建者生成任务与可执行检查。这里的“原子”就是可以独立替换、修复并再次组合的材料单元，而非模型内部表示。

关键变化发生在构建以后。教师智能体多次尝试仍不能完成任务时，系统不直接把它当成困难样本丢弃，而是诊断：是工具或记录缺失，是裁判要求了用户根本没提出的值，还是环境本来正确、教师能力不足。前两种进入修复，第三种保留为难题；共享服务原子的修复还能影响以后用它构建的环境。

最有信息量的证据来自第5.2节。第二轮接纳的4,662个环境中，教师每个尝试八次，至少一次被检查器接受的比例为71.6%；1,324个没有成功轨迹。作者诊断其中52%为检查器问题，23%为世界缺陷，25%为教师解决不了的有效任务。修复前两类并重新采样后，该比例达到88.3%。这是指定教师、八次机会和当前检查器条件下的产出率，不能解释成真实服务复现准确率。下游训练还提供用途证据，但环境修复与重新采样共同发生，也不能将提升全部归因于单一部件。

建议先读第3.5、5.2节及附录L，看清无成功轨迹如何被归因，以及修复的是哪一层。


## 2. When Agent Evaluation Becomes Unreliable: An Empirical Study of Oracle Failures and Configuration-Dependent Measurement in an LLM Agent Benchmark

[原始来源](https://arxiv.org/abs/2610.16067)｜2026-10-12；v2。

这篇把研究对象从智能体转向决定它是否成功的软件。作者发现，仅看成功率表格，看不出裁判在计算参考答案时是否污染了被评分环境。论文中的具体故障是：奖励函数重置数据库、运行参考解以生成目标状态哈希，却没有恢复智能体留下的状态。作者自己的外围运行框架在会话结束后再次读取数据库，于是读到的是参考解的结果。这是上游函数副作用与后续读者组合产生的集成故障；作者没有声称原基准自带运行器的成绩同样膨胀。

方法要求被审计对象提供建立新环境、取得状态签名、调用裁判等接口。随后用五项状态完整性约束和三个已知答案对照，检查裁判调用前后及不同输入条件下的行为；再主动注入七类缺陷，检验这套检查是否真的能发现错误，而不只是对当前实现给出“通过”。状态签名相当于数据库的可比较指纹，能发现裁判返回正确布尔值、却悄悄改动环境的情况。

v2报告七类注入错误均有检出，但按更细的可区分变体与目标组合计，只检出57个中的54个，不能写成无遗漏。对4,320次已记录运行，原有数据库通过标签为4,194个；在干净数据库重放工具调用后为2,883个。综合成功率由94.3%降到65.5%，两者不是同一指标的分子分母，且不同智能体修正幅度不同，比较次序也受影响。另一套独立基准因日志不足以重建参考终态而无法迁移审计，界定了方法的实际前提。

建议先读第3.2和4.1节，看清污染出现的调用时序及54/57的漏检边界。


## 3. C-World: A Computer Use Agent Environment Creator

[原始来源](https://arxiv.org/abs/2601.06328)｜2026-01-09；v2。

C-World要解决真实工具环境昂贵、难以持续扩展的问题。它把环境组织成工具集合、任务生成、状态变化和奖励四部分，并提供两种执行方式：真实模式把调用送往实时服务；合成模式由World Engine生成工具响应。任务先从候选工具组合生成，再检查工具覆盖和约束是否成立，反复修改；执行时还可以在中间层插入超时、限流或任务条件变化，观察智能体能否恢复。

模拟器的输入不只是当前工具参数，还包括工具结构、按邮件或日历等功能分类的人工说明卡、少量示例和整个会话调用日志。说明卡规定常见字段、响应形态和失败模式，日志则帮助后续响应延续先前状态。它逐步预测返回信息，没有生成一个与指定真实服务独立运行、可机械检查的数据库实现。奖励也混合了两种依据：结构及顺序约束可直接检查，完成度和语义合理性由多个语言模型投票判断。

作者比较真实执行和合成执行得到的模型排名，报告Spearman相关系数0.883。这个量表示模型之间强弱次序相近，不是88.3%的调用、状态或任务完全相同。正文还给出模拟执行成绩表；这比只展示合成任务可运行更接近“模拟评测有没有用”的问题，但相关排名仍可能掩盖某个模型的绝对成功率偏移。当前核验没有完整复核相关系数的逐任务配对样本与不确定性，因此不进一步解释其显著性或适用范围。

建议先读第3.2与5.4节，对照World Engine看到了什么，以及排名相关究竟比较了什么。


## 4. Scaling Laws for Tool-Use Agents via Controllable Environment Synthesis

[原始来源](https://arxiv.org/abs/2610.37648)｜2026-10-27；v1。

作者问的不是怎样把数据量继续做大，而是相同数据预算该分给更多应用、更多任务，还是同一任务的更多初始数据库。SynthAPI先生成应用功能说明，再写Python数据类型和读写这些数据的API；第二阶段生成用户任务、初始数据库、检查器和参考求解程序。智能体通过工具发现接口查找操作，提交Python代码调用工具，获得JSON结果。因此状态由可执行代码维护，不必每一步都让语言模型猜返回值。

流水线只保留初态不能通过检查、执行参考程序后可以通过检查的任务。参考程序能够看到整个数据库和内部标识，智能体需要自己查询获取信息，所以参考解是可解性检查，不是与智能体信息相同的基线。作者还控制每个初态中的干扰数据量：同样购买某个商品，可以只放必要商品，也可以增加更多无关记录。这使任务数量、工具覆盖和搜索复杂度有机会被分开研究。

研究覆盖458,752个任务、849个训练模型和四个模型规模。作者用环境组成及训练规模拟合预测下游表现的规律，并把训练计算量最高的四分之一运行留作外推检验。归一化下游分数的平均绝对误差为0.0285，而只使用任务数量的模型为0.1706；这个指标衡量预测误差，不是任务成功率。实验支持“数据组成不能被总条数替代”，并观察到预算增加后，工具和数据库多样性的收益比单纯追加任务更大。它没有测量对某个外部服务的行为重建误差。

建议先读第3节和图2、图3，看清应用数、任务数、初态数量及干扰数据怎样被分别控制。


## 5. APIFlow-Bench: Measuring Whether Agents Survive Long, Dependent API Workflows

[原始来源](https://arxiv.org/abs/2608.29128)｜2026-08-29；v1。

APIFlow-Bench指出，后端状态正确和最终把正确结果交给用户是两回事。它生成逐步依赖的REST工作流，每项从一个失败请求及真实错误提示开始。正文例子是令牌过期导致401，智能体需要沿提示恢复认证，再取回要求的读数与标识。任务在同一个合成API世界中向前生长，形成最长20个子任务的链，而不是把相互独立题目机械拼接。

检查分为两面：状态检查追踪模拟服务产生的特定标记是否通过要求的数据流到达目标工作区；最终答案则使用带类型的答案卡逐字段校验。这样，直接猜中答案不等于执行了规定工作，后端执行成功但答案字段错也不能算完整交付。生成阶段先测试检查器，再用参考求解器确认可解，组合后的链还做双向参考重放；独立对抗审查另发现六种评分漏洞并修复，说明自动准入并未穷尽问题。

作者发布13个世界中的467项任务，在共同运行框架下评估19个模型。摘要报告单项成功率93%，清洁切片的20子任务链为74%；加入所有模型都未通过的筛查单元后为61%。那些单元仍有通过检查的参考解，不能据模型共识断言任务无解。更值得注意的是，在清洁切片失败运行中，77%已经到达正确终态，却在最终交付失败；这个比例的分母是失败运行，不是全部任务。作者同时提醒样本量和生成体系纠缠限制了排名结论。

建议先读第4—5节及8.3节，看清状态通过与最终答案通过如何分开判定。
