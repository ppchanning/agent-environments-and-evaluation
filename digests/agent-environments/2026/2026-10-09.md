## 1. CTE-Bench: Counterfactual Trace Evaluation for Stateful Software Simulators

Xinran Zhang，正文署名Independent Researcher；预印本，首发2026-09-29，核验v1。**近30天补读**。[原始摘要](https://arxiv.org/abs/2609.36647) · [正文](https://arxiv.org/html/2609.36647v1)

作者问的是：模型见过一段服务调用历史后，如果服务规则或内部状态突然变化，它能不能正确推演接下来的调用？普通轨迹评分把所有返回都混在一起，大量调用其实不受改动影响，继续照旧回答也能拿高分。因此本文刻意构造“原来的服务”与“发生改动的服务”两个执行版本，找出哪些后续返回真正被改动影响，再单独评价这些位置。

模型收到完整Python源码、此前调用及真实返回、一项明确干预，以及固定的后续调用。干预可能是改源码中的一个比较条件，也可能直接改时钟或计数器。参考执行器恢复历史结束时的状态，应用干预，运行未来40个调用，给出逐步答案。论文中的限流器例子把拒绝条件从amount≤0改成amount≤1：一次增加1的调用现在被拒绝，计数不再增长，后面的查询与重置结果也随之改变。这要求模型同时理解改动的直接作用和沿状态传播的后果，不能只改当前返回。[方法与示例](https://arxiv.org/html/2609.36647v1#S3)

测试有255个场景，覆盖认证、银行、购物车、文件系统、限流和预约六类确定性服务，每模型要预测10,200次返回，其中2,476次属于干预影响位置。作者比较四个模型，并分别让模型在每步后收到正确历史、完全不收到后续反馈，或把自己的预测当作后续历史。返回由执行器按规定比较。直接重放未改动服务的答案，全体调用能得75.7%，但影响位置得0；四模型有正确反馈时，影响位置准确率约54.3%—61.5%，没有反馈则降至23.2%—28.9%。这支持“历史纠正能缓解连续推演错误”，而不是证明模型已经掌握服务。限流场景占105个，其余各30个，平均分还受到任务配比影响。[实验](https://arxiv.org/html/2609.36647v1#S4)

阅读建议：先看Figure 1与§3的干预和记忆协议，再看结果表，确认“全部调用”与“影响位置”的分母为什么会给出不同判断。

## 2. Fault Injection in OpenAPI Specifications for Evaluating Black-Box Testing Effectiveness

Hamza Bin Mazhar、Yuqing Wang、Mika V. Mäntylä；预印本，首发2026-07-13，核验v1。**旧文补读**。[原始摘要](https://arxiv.org/abs/2607.12101) · [正文](https://arxiv.org/html/2607.12101v1)

这篇研究的是测试工具遇到不准确接口文档时，会发生什么。接口测试通常默认OpenAPI说明书可信，但真实文档可能漏掉必填项、写错限制、弄错方法或响应结构。工具表现下降时，原因可能是获得的信息变差，而不是探索算法变弱。作者因此保持服务实现不变，只修改工具读到的文档，以分离这两个因素。

修改分六类：把请求限制写得更严、删除请求限制、改HTTP方法、改响应判定规则、破坏引用，以及混合修改。工具仍然对原服务发请求，服务按真实实现处理，而不是按被改过的说明书处理。例如文档不再告诉工具某字段有边界，它可能大量发出被服务拒绝的值。实验逐级扩大被修改操作的比例，并使用三个随机种子、每次重置环境，在TrainTicket与SocialNetwork两套微服务系统上比较EvoMaster、RESTler、Schemathesis。[实验设计](https://arxiv.org/html/2607.12101v1#S3)

作者同时检查源码行与分支是否被执行、文档操作是否被调用且至少成功一次、返回状态码比例，以及执行日志的多样性。这些指标看的是不同事情：请求触及某操作不代表形成有效状态变化。结果中，删除请求限制可以让代码覆盖和操作覆盖几乎不变，却显著损害请求质量；改HTTP方法则往往让多类指标一起下降。论文还分析了反常现象：RESTler的5xx比例下降，有时是依赖链被破坏、工具根本进不了容易出错的深层路径，不能解释成测试更好了。三种子范围给出了重复运行的波动；作者没有用这么小的重复数包装稳定的置信区间。[结果Table III与讨论](https://arxiv.org/html/2607.12101v1#S5)

阅读建议：先读故障分类与Table III，再读RESTler的反常案例，看清覆盖率没变时服务交互究竟损失了什么。

## 3. AutoRestTest at the SBFT 2026 Tool Competition

Tyler Stennett等，团队含Georgia Tech、AWS AI Labs、IBM Research与University of Georgia；SBFT 2026工具竞赛论文，arXiv首发2026-07-01，核验v1。**旧文补读**。[原始摘要](https://arxiv.org/abs/2607.01063) · [正文](https://arxiv.org/html/2607.01063v1)

很多API操作不能孤立测试：先创建对象拿到ID，后面的查询、修改和删除才有有效输入。随机生成请求会把预算花在缺参数或缺前置状态的失败上。AutoRestTest把探索拆成选择操作、参数、值与跨操作依赖四个决策，让它们共同根据真实响应调整，而不是一次性由语言模型生成长测试序列。

工具先从OpenAPI建立操作依赖图。节点是操作，输入参数与其他操作输出的语义相似性提供初始连边，交互反馈继续更新依赖。语言模型在预处理阶段为每个操作提出有领域含义的值，并调用目标验证；失败后用响应重新生成，最多尝试三次。最后一次仍失败的值也会保留，所以这里不是“所有输入已经验真”。正式探索时，四个决策各有一张Q表，记录过去选择带来的奖励，初期多尝试，后来更多利用已有高分选择；生成请求后还会替换类型、边界值等以触发异常。[方法§2](https://arxiv.org/html/2607.01063v1#S2)

奖励同时偏向2xx与5xx：前者帮助建立成功调用链，后者用于寻找服务错误，其他状态码受到惩罚。竞赛组织者在11个真实REST API、共317个操作上，每工具每API运行10次，每次一小时，比较六个黑盒工具。按这篇参赛报告，AutoRestTest在故障发现、随时间积累的效率以及最终综合效果三类规范化评分均居首；平均发现67.09个按竞赛规则归并的独特5xx错误，下一名24.65个，平均覆盖17.27个操作。这里的“错误”不等于经人工确认的独立根因。正文也报告了一个航班搜索API因响应编码假设而崩溃，说明协议处理仍可能阻断探索。[竞赛结果§3](https://arxiv.org/html/2607.01063v1#S3)

阅读建议：先读§2.1—2.4，再读§3的计分口径，想清依赖图可以保留哪些机制、哪些奖励必须随重建目标改变。

## 4. ToolSandbox: A Stateful, Conversational, Interactive Evaluation Benchmark for LLM Tool Use Capabilities

Jiarui Lu等，Apple；核验2024-08-08首发的arXiv v1及Apple原始介绍。**旧文补读；权威团队优先名额**。[原始摘要](https://arxiv.org/abs/2408.04682) · [正文](https://arxiv.org/html/2408.04682v1) · [Apple介绍](https://machinelearning.apple.com/research/toolsandbox-stateful-conversational-llm-benchmark)

ToolSandbox想解决的是：调用工具的参数写对了，任务就一定完成了吗？很多实际操作依赖环境当前状态，而且用户可能没有一次说清全部信息。只看一次函数调用或最终聊天回答，会看不到前提没满足、对象改错或凭空填参数等失败。因此它提供会实际执行工具、保留数据库状态的环境，并把过程中的关键状态变化也纳入评价。

代理接收用户消息和工具说明，工具参数转成Python调用，由执行环境真实运行，错误通过异常返回，状态延续到下一轮。论文的短信例子中，蜂窝服务关闭时发送会失败；代理需打开服务、找到正确联系人，再发送。评价不要求所有合法动作严格按同一条轨迹出现，而是把必要事件组成有先后约束的图：开服务和找联系人可以互换顺序，但发送必须在它们之后，最终消息数据库还要出现正确号码与相应内容。系统在实际轨迹里寻找满足约束的最佳匹配。另设不允许出现的事件，例如不知道当前时间却捏造时间去计算差值；触发后整条任务得分归零。[执行与评价§2](https://arxiv.org/html/2408.04682v1#S2)

原版有34个工具、1,032个由两名内部专家构造和交叉验证的场景，比较多个当时的闭源模型，并改变工具名称、描述和干扰工具等条件。表中成绩是里程碑相似度与禁区规则合成的平均分，不能简单读成完整任务成功百分比。作者还人工标注1,032条GPT-4o用户模拟器与代理的轨迹，比较用户模拟提示：加入知识边界和对话示范后，幻觉错误由12.4%降至6.97%，指令遵循错误由6.20%降至0.77%。这说明互动评测本身也会受模拟用户质量影响，而不是所有失败都来自被测代理。[场景与实验](https://arxiv.org/html/2408.04682v1#S3)

阅读建议：先看Figure 1与§2.3，区分工具执行产生的真实状态、人工事件约束以及最后汇总得分三者。

## 5. Weblica: Scalable and Reproducible Training Environments for Visual Web Agents

Oğuzhan Fatih Kar等，Apple；arXiv首发记录2026-05-07，页面仅列v1。**旧文补读；权威团队优先名额**。[原始摘要及版本记录](https://arxiv.org/abs/2605.06761) · [正文](https://arxiv.org/html/2605.06761v1)

Weblica的问题是网页代理训练受在线网站不稳定、网络延迟与交互环境数量不足限制。它用两种办法提供可重置的环境：缓存真实网站HTTP交互，以及根据真实浏览中需要的能力生成新网站。作者目标是获得便宜、多样的训练场景，不是逐个还原某个网站的全部后端行为。

缓存路线先让代理访问网页，记录请求及响应；重放时按请求特征找缓存，处理时间戳和会话等变化，对没命中的请求使用模糊匹配或特定补偿规则，并在隔离网络条件下检查任务还能完成。生成路线则分析代理成功与失败轨迹的截图，提取能力，例如选日期或操作下拉菜单，再让编码代理按不同网站类别和视觉样式制作HTML、JavaScript、CSS。合成站点没有真正后端，购物车等会话状态由localStorage保存；编码代理用截图自检。训练部分合成环境有2,560个站点、44,227项任务。[环境构建§3](https://arxiv.org/html/2605.06761v1#S3)

实验把这些环境用于微调与强化学习，再让视觉代理依据截图和URL点击、输入。在三套真实网页任务基准上，同为每次30步、一次尝试，训练后8B模型的平均任务成绩从24.8%升至35.6%，每个实验重复三次；任务结果按各基准的判定器评价。作者还比较仅缓存与仅合成的训练条件：合成在多数基准较好，缓存在购物类DeepShop略好。增加尝试次数还能提高成绩，但那同时增加了总动作预算，不能把多次尝试成绩与单次成绩视为同成本。这些结果支持环境可用于训练并迁移到在线导航，没有测它们是否忠实再现原网站所有状态转移。[实验§5](https://arxiv.org/html/2605.06761v1#S5)

阅读建议：先读§3.2—3.3，再看§5.4与§6，弄清缓存的未命中处理、合成站点状态能力以及训练迁移证据各自覆盖什么。
