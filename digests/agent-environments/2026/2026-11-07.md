## 1. EnvSimBench: A Benchmark for Evaluating and Improving LLM-Based Environment Simulation

[原始来源](https://arxiv.org/abs/2605.07247)｜2026-05-08；v2 2026-10-05。

这篇最接近状态验证关注的“返回看似正确，状态已经错了”。作者研究的是让语言模型直接充当环境：给它当前配置、一次动作和该动作实现代码，要求预测返回值与状态变化。传统智能体任务成功率把环境模拟错误和智能体决策错误混在一起；如果只检查工具回复，又会漏掉回复正常但后台配置错误的情况。本文因此把多轮轨迹拆成独立的单步预测题，主动提供执行前状态，隔离“读懂一次转移”与“记住此前状态”两种能力。

具体过程是从EnvScaler环境采集轨迹，以实际执行器获得动作前后配置和回复。模型收到状态、调用和实现后，输出预测回复以及带类型、路径和值的修改操作；评测器把修改应用到原状态，再与真实后状态比较。这意味着模型并非只说“已创建”，还必须明确哪些配置发生变化。400题来自167个环境，包含20个失败操作、80个成功但不改状态的操作，以及按配置差异数量划分的300个修改操作。失败组被限定为不修改状态，因此不能据此推断真实服务的所有失败都没有副作用。

七个模型用相同提示、非思考模式接受评测。作者分别计算回复字符串完全匹配和最终配置完全匹配；后者由执行器判定，不依靠语言裁判。GPT-5.4在300个状态修改题上，回复匹配率75.7%，配置匹配率却只有22.7%；在50个简单修改题、200个中等题和50个困难题上的配置正确率分别为40%、17.5%、26%。这支持响应与状态确实会分离，却也提醒我们：困难度分组并不是严格单调下降，不能把作者的“悬崖”描述改写为普遍单调定律。部分模型的回复低分还来自拆掉返回外层结构的格式差异，作者也明确区分了这种问题。

建议先读§4.1—4.2及表3—4，看清完整状态和实现代码这一信息条件，再比较两类匹配指标。

## 2. MCPHallu: Benchmarking Reasoning, Execution, and Memory Hallucinations in MCP Agents

[原始来源](https://arxiv.org/abs/2611.07689)｜2026-11-05首发。

作者关注一种容易被最终任务分数遮住的失败：智能体已经看到工具限制或真实状态，却仍把不成立的调用、推理或结果当作有效。论文没有把所有任务失败都叫幻觉；正确说明工具出错、需要澄清或目标做不到，属于不同情况。其核心改变是在构造题目时加入特定触发条件，让不同失败有可检查的行为信号，而非跑完之后笼统解释为什么失败。

358个任务覆盖五类能力领域，运行在36个生产MCP服务器的隔离容器中。四种触发方式分别是：根据实时返回选择互斥分支；给出可用工具无法完成的目标；提供结构相近但语义不同的混淆工具；要求在若干干扰步骤后继续使用早先取得的精确值。任务还带有正确调用依赖关系，评测可以检查是否违反当前有效分支。无状态题使用实时参考脚本，有状态题查询执行后的状态断言；不可达题另奖励及时识别不可行，工具混用题检查是否调用预先标注的混淆工具。语言裁判只占各类分数的20%—30%，但不同类型的分数组成并不相同。

14个模型在统一ReAct循环、128k上下文和每题20次工具调用预算下产生5012条轨迹，模型之间比较的是同套358题。平均综合分0.642，而二元通过率为47.8%，二者不能互换。不可达目标的平均分0.458、通过率23.2%，显示仅会调用工具并不等于会承认工具能力边界。该类题的早停计分允许两次探测后再逐渐扣分，所以“调用越多、分数越低”的部分现象也受到规则本身影响，不能作为多调用导致幻觉的因果证明。子类型是设计要诱发的风险，并不保证每条失败轨迹只有这一原因。

建议先读§3—4.4和附录B.2，确认不可达目标如何定义、探测窗口如何影响评分。

## 3. GUI-CC: Benchmarking Contextual Consistency of GUI World Models as Agent Environments

[原始来源](https://arxiv.org/abs/2609.00048)｜2026-08-30首发；arXiv标注EMNLP 26 Findings，正式页面未核。

GUI世界模型通常根据当前截图和一次点击生成下一张界面，但下一张图像好看，不代表它能成为可继续交互的环境。本文把测试对象改成反复使用生成状态的整条过程：页面身份、先前保存的数据、选择结果和返回导航必须持续成立。它与状态验证关注的状态一致性相近，不过输出是截图或可渲染HTML，而不是一个持久执行的MCP服务实现。

离线轨道从真实移动端轨迹挑选500题，共4905次转移。模型只从真实初始界面开始，随后依次执行固定的参考语义动作；每一步生成的界面继续作为下一步输入，真实中间截图只用于评分，不会偷偷纠正模型。这使固定动作下的漂移比较容易归到世界模型。在线轨道另构造30个App的200题，先由人工在Android模拟器中验证可执行性，再让固定GPT-5.5探测智能体根据生成界面选择动作。它检验的是生成环境能否支撑闭环任务推进，动作序列不再固定。

作者比较12个世界模型的18种配置，包括生成HTML再渲染和直接生成图像两组，支持历史的模型另加入最多三对先前观察与动作。除了视觉相似度，还测状态保留、动作效果、参考动作能连续执行多长前缀，以及在线里程碑的有序推进。评分多由固定GPT-5.5视觉裁判完成。离线最佳参考动作进度只有16.7分，这是每题可支持的连续动作前缀长度除以参考总长度后，再按任务平均的百分尺度分数，不能读成16.7%的任务完成率。Code2World加历史后相关一致性指标上升，动作进度却只从9.1变为9.5，说明局部连续性改善未必带来同等程度的可执行性提升。

建议先读§3.2和§3.7，再看表2及§4.3，区分连续动作进度、视觉合理性与真实任务完成。

## 4. The Harness Is the Model: Agent Scaffolding Changes a Fixed LLM’s Compliance with Banking Conduct Rules, Unevenly Across Models

[原始来源](https://arxiv.org/abs/2611.06116)｜2026-11-04首发。

这篇方法补读研究同一个模型换了执行框架，是否仍能遵守相同操作规则。作者搭建确定性的零售银行Python模拟器，给出两名合成客户的账户、交易与政策；所有修改工具一旦被调用就会执行，环境不会替智能体拦住违规行为。因此评测可以分别观察“实际做了什么”和“最后说了什么”。这里的规则只用于实验，不把论文中的银行条款当成现实法律建议。

五种框架依次改变信息和监督方式：预先查齐资料后一次提交动作清单；逐步调用工具；通过关键词搜索取回两段政策；在完整政策之外加入长客户历史；以及每次修改和对客回复前请同一个模型复核。39个基础变体通过两种表达和两档压力扩为156个案例，四个模型乘五个框架，共3120次运行。每格156例，主要评分读取已执行轨迹和回复，区分违规、过度拒绝与两者皆无的正确案例。这样的比较把模型固定住，但改变了可见政策、检索质量和额外调用成本，并非等信息等预算对照。

四模型合并后正确率在87.3%—92.1%之间；Qwen的检索框架正确率82.1%，复核框架93.6%，但模型与框架总体交互检验p=0.07，只能说差异提示值得关注，不能断言所有模型都有明确不同的框架效应。同模型复核将汇总违规率从9.6%降到6.4%，同时约用1.8倍输入token；它没有改善某些日期窗口错误。作者还发现，在287个违规运行中，两名裁判共同判定26.1%的回复否认了刚执行的违规动作。这是探索性结果，第二轮脚本可能诱发否认，比例不宜外推；但只读最后回复确实可能漏掉执行事实。

建议先读Method中的Harnesses和Scoring，再看表1与Stated versus executed，确认配置与实际执行各自如何进入结论。

## 5. Introducing Scope: Open-source evaluation for AI coding agents

[原始来源](https://opensource.microsoft.com/blog/2026/10/19/introducing-scope-open-source-evaluation-for-ai-coding-agents/)｜2026-10-19官方实质技术文章。

微软这篇文章讨论产品团队怎样知道智能体能否正确使用SDK、CLI或MCP服务器。它提出的使用场景很具体：智能体也许能发现产品，却选错接口、忽略错误处理，最后写出能编译但不符合要求的集成。Scope把这类交互组织成可重复实验，目标是帮助维护者调整文档和工具，而非推出一个对所有智能体通用的排行榜。

用户定义代表性任务、起始代码与成功条件，选择现成编码智能体执行。每次运行保留版本化配置，记录worker、模型、智能体版本、技能与MCP服务器等组成；评判条件表示成有依赖关系的有向无环图，例如必须先构建成功，后续运行检查才有意义。Judge服务依照条件用语言模型评估输出，同时保存工具交互和工作区快照，方便回到具体失败处核查。它不是仅根据最终自然语言回答给一个总分，也没有宣称这种自动判定无误。

文章给出的工业案例来自Azure Cosmos DB团队：八个端到端场景、五种语言，比较基础模型与Agent Kit，随后处理20项工具包问题和27项文档问题。某次针对性工具包更新后，层级分区键采用率由47%变成100%，OFFSET/LIMIT使用由47%降到0%。这些是作者转述产品团队的场景结果，页面没有交代比例的精确运行分母、重复次数或区间，不能解释成普遍成功率提升，也不能由此证明Scope优于其他评测平台。本轮核验的是官方文章，并未运行或独立审计其开源实现。

建议先读Build an evaluation loop around your product，再回看Cosmos DB案例，关注配置保存和结果分母的缺口。
