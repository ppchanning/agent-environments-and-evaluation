## 1. REST API Testing with Verified LLM-Inferred Dependencies and Response-Driven Refinement

来源：[原始页面](https://arxiv.org/abs/2608.17546) · [全文入口](https://arxiv.org/html/2608.17546v2)；Tu Nguyen; Thanh Nguyen; Huy Nguyen; Viet Nguyen; Tien N. Nguyen; Vu Nguyen；首发 2026-08-18，核查版本 v2（2026-08-20）；preprint。

API测试经常卡在“参数看起来合法，却始终走不到目标操作”。原因不只是字符串格式错误：后一次请求可能需要前一次创建或查询得到的资源标识，而且同名的id未必指同一种对象。作者针对已有LLM方法的一处缺陷：它们容易把模型推测的依赖直接放进调用图，后面再围绕错误关系生成大量无法执行的测试。APIPilot改变的是依赖进入测试生成之前的验证步骤。

输入是OpenAPI说明和可调用服务。系统先结合字段结构与LLM语义判断，提出“这个响应字段可以供那个输入使用”的候选关系，再真实执行生产者、取出具体值、传给消费者。关系有候选、验证、拒绝或修订等状态；反馈支持的关系才用于构造调用图。验证也不是要求每次请求完全成功，而是判断请求是否越过了缺资源或参数障碍，因此其含义是当前上下文中的可行证据。测试生成随后在图上进行有界的多条路径搜索，运行过程中维护可用资源值，并根据响应修订输入限制和依赖。论文中的GitLab例子说明，查询已有项目与提交可以接上讨论操作，不必总假定要从创建资源开始；另一种错误是把project id当成namespace id，响应会揭露这种字段映射问题。

作者在16个REST服务上比较AutoRestTest、RESTifAI、KAT、DeepREST；LLM方案使用同一GPT-4.1-mini、温度0，实验重复五次取平均。操作覆盖率指成功调用到的操作占比，APIPilot平均92.3%，AutoRestTest为70.4%、RESTifAI为79.0%。流程成功率为771/875，即88.1%，但不同工具生成的流程集合不同，这不是同一批等难度流程上的胜率。文中197个独特5xx失败也不能解释为197个已确认根因：其中OhSome占110个，去掉该服务后，优势并不一致。这些结果支持响应验证能帮助到达更多接口行为，尚不足以证明任何预算下都优于其他策略。

与仿真验证的关系：模型猜测的依赖可按真实响应赋予证据等级，验证调用预算应明确记录。真实REST服务测试不是服务模拟器；生成测试时淘汰无效流程，也不能成为仿真删除失败响应与副作用的理由。

阅读建议：依赖验证与响应修订、操作覆盖表；结合方法、结果与限制阅读。

## 2. Detecting and Mitigating Flakiness in REST API Fuzzing

来源：[原始页面](https://arxiv.org/abs/2603.28452) · [全文入口](https://arxiv.org/html/2603.28452v1)；Man Zhang; Chongyang Shen; Andrea Arcuri; Tao Yue；首发 2026-03-30，核查版本 v1（2026-03-30）；preprint。

同一测试有时通过、有时失败，可能不是代码改坏了，而是返回值依赖时间、资源状态、运行环境或返回顺序。作者研究的是这种不稳定性在REST系统测试中的表现。它比单元测试更难处理：一次测试可能是一串有状态请求，前一步留下的资源、异步完成时间和数据库状态都会影响后一步；固定软件版本不能自动消除这些变化。

作者用EvoMaster的黑盒和白盒模式测试36个API，在两个运行环境中观察到31个API出现不稳定测试，并人工分析近3000个失败测试，归纳出九类来源。FlakyCatch在生成测试后，按相同配置与环境重跑，比较状态码、响应头和正文；出现差异就标为潜在不稳定。只重跑一次也可能偶然碰到相同结果，所以它还用模式规则识别时间、随机标识、密码学产物和运行时消息。接着把差异定位到具体断言，保留稳定字段的检查，将不稳定断言注释并注明两次值。论文中的时间字段例子因此不再要求精确匹配某一个时刻，而不是整条请求都被删除。

处理效果实验中，每种EvoMaster模式使用一小时搜索预算、重复十次，生成的测试在原生成环境中各执行100次。作者比较处理前后的失败率，并区分每次都失败与间歇失败。结果并非全体服务都被治好：表5仍有失败率升高或几乎不变的行；在同一环境检测也捕捉不到换环境才出现的问题。更重要的是，注释断言会直接减少可失败的检查，因此失败率下降本身不能证明缺陷检出能力保持不变。作者保留其他断言的设计有实际价值，但这种取舍需要按字段审查。

与仿真验证的关系：先重复执行参考服务，再解释模拟器与参考端的差异。字段级记录比全部屏蔽id更可靠：随机标识可以变化，但后续查询与对象绑定仍须一致。自动屏蔽断言减少检查能力，失败率下降不等于缺陷检出能力不变。

阅读建议：5.1—5.3节与表5；结合方法、结果与限制阅读。

## 3. Gecko: A Simulation Environment with Stateful Feedback for Refining Agent Tool Calls

来源：[原始页面](https://arxiv.org/abs/2602.19218) · [全文入口](https://raw.githubusercontent.com/mlresearch/v306/main/assets/zhang26cv/zhang26cv.pdf)；Zeyu Zhang; Guohao Li; Zhenchang Xing; Alexandros Apostolopoulos; Yu Lin Lee; Liang Zheng；首发 2026-02-22，核查版本 arxiv v2; formal ICML2026 PDF（2026-06-09）；conference_paper。

Gecko解决的是agent正式使用工具之前，能否先在模拟中修正调用计划。直接在真实服务上试错既昂贵，也可能已经造成取消订单之类的后果；单纯让模型反思又缺少执行反馈。作者把模拟器做成有状态的反馈环境，而不是只生成一段看起来像API返回值的文字。

输入包含工具说明、用户目标和待执行调用。规则先检查工具名、必填参数与类型，LLM补充语义检查；通过后，另一个模型结合工具schema和当前任务状态生成响应。状态估计器根据调用更新进度，任务反馈模型判断目标是否完成、还有什么未满足。规划模型据此改写调用并重试，这套过程称为GATS。论文图2的例子中，临时目录建在文档旁边而不是文档内部，反馈把这种“调用合法但目标没实现”的问题指出来。模拟成功的调用序列最终作为真实agent的指导加入输入；真实agent仍要重新调用工具、核查模拟值，不是把模拟结果直接交付给用户。

作者在BFCLv3和τ²-bench上评测最终工具使用表现。正式正文报告GPT-4o在BFCLv3的综合准确率由76.93%到84.62%；它是该基准不同类别汇总的任务表现，不是8578个工具的行为复制率。τ²任务还有一个重要条件：只读查询使用真实数据库，写操作才模拟，因为隐藏订单或航班信息不能可靠凭空生成。工具调用评测由各基准规则判断结果，模拟中另有LLM判断任务进展，两者不能混为一个裁判。收益还伴随额外规划和辅助模型成本，文中的重试实验显示第一次重试收益较大、后续收益递减。

与仿真验证的关系：Gecko围绕用户目标提供有用状态与反馈，其下游成功率不等于服务级行为保真。语法合法、状态变化和目标完成应分别检查；辅助模型成本及真实只读查询权限也应进入比较条件。

阅读建议：第3节、GATS流程及附录H/I；结合方法、结果与限制阅读。

## 4. Intelligent REST API Data Fuzzing

来源：[原始页面](https://www.microsoft.com/en-us/research/publication/intelligent-rest-api-data-fuzzing/) · [全文入口](https://patricegodefroid.github.io/public_psfiles/fse2020.pdf)；Patrice Godefroid; Bo-Yuan Huang; Marina Polishchuk；首发 2019-11，核查版本 ESEC/FSE2020（2020-11）；conference_paper。

RESTler解释了怎样沿资源依赖到达深层状态，这篇继续问：到达某个操作后，请求体到底该怎样变化，才能发现更多服务规则和异常？只把字符串换成乱码并不够。JSON请求体是树状结构，字段的缺失、重复、类型变化和组合都可能触发不同处理路径；全部枚举则会迅速耗尽预算。

方法以RESTler的状态调用序列为基础，把请求schema表示成树，提供删除子节点、仅保留某个子节点、复制节点和改类型四类操作；再限定变化发生在单节点、一条树路径或任意节点集合。变异后的结构需要填入具体值。作者不仅使用固定默认值，还研究从说明中的示例和之前服务响应提取值，避免请求在早期格式检查就失败。论文的DNS例子必须先有DNS zone才能操作其中的record set，显示有效资源上下文和负向请求体变异可以同时存在。

初步比较选择Azure DNS：共有13种请求，四种具有非空请求体；每种节点规则与树规则组合至多生成每个请求1000个变体。因为不能插桩云服务，作者用“错误码＋去除时间、会话标识等运行信息后的错误消息”作为错误类型，比较发现了多少种不同类型。任意节点组合理论上更广，却会在有限预算内反复探索冗余组合；路径变化有时反而更有效。随后把选出的组合用于多个Azure服务，数百次内部服务器错误被人工归并为17个可复现、开发者确认的独特bug。这个数字是确认根因数，不能与现代论文的独特5xx响应数直接排行。

与仿真验证的关系：固定资源与调用上下文后，定向改变字段或结构路径，可观察错误类别和状态后果。本文在真实云服务上探测，未提出MCP模拟器；迁移测试思想时要重新定义接口与判据。参考服务的异常行为也属于需要描述的行为范围。

阅读建议：3节与3.3错误类型、5节值来源；结合方法、结果与限制阅读。

## 5. Log-based, Business-aware REST API Testing

来源：[原始页面](https://arxiv.org/abs/2604.08007) · [全文入口](https://arxiv.org/html/2604.08007v1)；Ding Yang; Ruixiang Qian; Zhao Wei; Zhenyu Chen; Chunrong Fang；首发 2026-04-09，核查版本 v1（2026-04-09）；preprint。

OpenAPI往往能写清参数类型，却写不全业务过程。像GitLab这样的服务，操作之间不仅共享资源id，还要求对象处于特定业务阶段。LoBREST研究能否利用历史请求日志，把已经发生过的业务约束带入测试，减少只根据接口规格胡乱组合操作造成的不可达请求。

输入是规格、服务和历史请求日志。系统先分析操作与资源关系，再利用资源重叠和时间局部性，把长日志切成较短的业务片段；用户的资源标识、token或cookie等上下文分别维护，避免混用。片段还可能缺少创建资源的前缀，或完全没有某些操作，因此它补全资源并为遗漏操作添加片段。之后以这些片段为种子做业务感知变异，尽量保留使流程成立的约束，同时产生新的参数和请求组合。这里日志不是一份最终答案，而是生成后续测试的起点；系统仍执行请求、利用返回值维护资源。

作者比较17个服务和八种工具，其中16个较小对象包括REST测试集及GitLab子服务，另一个是完整GitLab。实验重复20次，小服务每次一小时，完整GitLab每次24小时。完整GitLab有1099个操作、109个模块，LoBREST平均覆盖352.7个操作，约32.1%，并触达80个模块；作者报告操作覆盖比黑盒EvoMaster相对提高188.6%。这确实支持日志种子帮助探索大服务，但32.1%也说明远非完整行为覆盖。更关键的是，实验日志由参与者模拟使用收集，并不是自然生产流量的随机样本；日志的信息质量和覆盖范围会影响优势。

与仿真验证的关系：输入轨迹包含可达业务状态，切片与补全能帮助初始化探测。应分别报告日志已有覆盖和额外探测覆盖，避免把材料提供的信息算成算法发现。真实服务测试及日志种子不证明未出现的服务规则已重建。

阅读建议：日志切片、补全、完整GitLab实验；结合方法、结果与限制阅读。
