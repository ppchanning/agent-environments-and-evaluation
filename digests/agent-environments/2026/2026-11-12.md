## 1. RESTestBench: A Benchmark for Evaluating the Effectiveness of LLM-Generated REST API Test Cases from NL Requirements

**需求关系比“能跑通”更重要**

来源：[原始来源 1](https://arxiv.org/abs/2604.25862) · [原始来源 2](https://arxiv.org/html/2604.25862)

首发：2026-04-28；版本：v1；类型：conference_paper。

RESTestBench使用3个真实REST服务、106条自然语言需求与228个变体，评估10个模型、每种设置3次重复。它比较简短和精确需求，以及单次生成与最多3轮执行反馈。对象是真实服务测试，不是新提出的模拟器。

作者发现，来自有缺陷实现的反馈可能降低测试的缺陷检出能力，模糊需求时尤其明显。例如两个用户的邮件地址互换，单看返回值是否属于允许集合仍可能通过，必须检查用户与地址的对应关系。

对服务仿真验证的启发是把业务关系写进独立验收条件，避免用当前实现反向定义正确行为。跨服务适用性仍受样本和需求质量限制；先读§3.2–3.4与§4.2，查看变体怎样对应原始需求。

## 2. RBCTest: Leveraging LLMs to Mine and Verify Oracles of API Response Bodies for RESTful API Testing

**为响应体提取可执行关系**

来源：[原始来源 1](https://arxiv.org/abs/2504.17287) · [原始来源 2](https://arxiv.org/html/2504.17287)

首发：2025-04-24；版本：v4；类型：conference_paper。

RBCTest从OpenAPI与文档中提取请求—响应及响应内部关系，生成Python检查，再借助示例过滤不可靠规则。这是REST API测试预言机方法，可支撑工具服务仿真的响应验证，但它自身不是环境生成器。

表7报告694条正确、63条错误，精确率91.7%；分母是受评规则，不能改写为任务成功率或完整业务覆盖。avatar与avatar_url的错误映射说明，名称近似不保证语义对应；AGORA+动态证据可补足部分文档稀疏情形。

规则不匹配不自动等于确认的软件缺陷；单次API关系也不能替代跨调用状态不变量。先读§5–6、§8.1.5与表7，分别核对规则来源、过滤机制和错误样例。

## 3. Widening Harm Evaluation Coverage with a Judge that Reads the World

**把轨迹与最终世界状态分开判读**

来源：[原始来源 1](https://arxiv.org/abs/2611.02624) · [原始来源 2](https://arxiv.org/html/2611.02624)

首发：2026-11-02；版本：v1；类型：preprint。

Widening Harm Evaluation Coverage with a Judge that Reads the World在DecodingTrust Arena的两个环境和OSHarm中，比较只看轨迹与回复、只读执行后环境且屏蔽轨迹、以及两者结合的裁判。模型、量表与推理设置相同，关注替代路径能否逃过原有检查。

读取最终环境可以发现轨迹检查遗漏的结果，但没有执行前状态时，裁判无法区分某对象被删除与它原本不存在。短暂发生后被恢复的伤害则需要过程证据。拒判和弃权必须保留，比较还受双方均给出决定的子集约束。

HTML表2标题、注释与正文的分母描述存在冲突，因此这里不引用摘要中的提升百分比。此工作提供环境验证思路，不能宣称模拟保真度已经被证明。先读裁判输入隔离和失败分析，并检查每项结果的判定覆盖率。

## 4. Sandboxing Untrusted AI Agents at Scale: Google Donates Agent Substrate and gVisor to the CNCF

**隔离、恢复与外部状态边界**

来源：[原始来源 1](https://opensource.googleblog.com/2026/11/sandboxing-untrusted-ai-agents-at-scale.html) · [原始来源 2](https://opensource.googleblog.com/2026/11/sandboxing-untrusted-ai-agents-at-scale.html)

首发：2026-11-05；版本：未标注；类型：official_technical_article。

Google官方工程文章介绍Agent Substrate与gVisor：Actor保存状态，Worker承担计算；暂停时缓冲请求，唤醒后由热Worker恢复内存和磁盘，再处理请求。gVisor在用户态隔离系统调用，文章也讨论microVM选项。

这些机制有助于组织可暂停的有状态执行环境，但恢复同一个已有环境，不等于从轨迹重建未知服务。外部API、数据库、时钟和未纳入快照的依赖仍决定恢复后行为是否一致。

快速恢复属于工程方的描述，缺少统一工作负载、状态规模及上下文条件的对照数据，故不列数值性能保证。它支撑仿真基础设施讨论，本身没有证明模拟服务行为正确。先读Actor/Worker生命周期与隔离边界；本笔记不涉及部署或安装。
